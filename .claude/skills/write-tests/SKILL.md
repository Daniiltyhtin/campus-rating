# write-tests

**Вход:** план и номер юнита. **Результат:** тесты и отчёт. Меняешь только тестовые пути (`backend/src/test/**`, `frontend/src/**/*.test.ts(x)`, `e2e/**`) и фикстуры.

## Шаги

1. Прочитай тест-сценарии юнита и связанные AE. Проверь, что покрыты все применимые категории: основной путь, границы, ошибки и отказы, интеграция через слои. Недостающее добавь из Goal и Approach юнита.
2. Если у юнита есть побочные эффекты (проводки, письма, события) — отдельный сценарий на повторное выполнение и ретраи.
3. Тест вызывает код так, как его вызывает пользователь, и проверяет видимый результат. SQL и транзакции — Testcontainers, не моки. UI — локаторы по ролям, без `force`.
4. Для доменного юнита это приёмочные тесты **до реализации**: убедись, что они падают по ожидаемой причине (нет класса, нет эндпоинта, неверный результат), и зафиксируй это в отчёте.
5. Отчёт: файлы тестов, сценарий → тест, как падали (red), что не удалось покрыть и почему.

## Границы

- Задача требует правки production-кода — верни ограничение и не правь.
- Не подгоняй ожидаемые значения под текущее поведение кода: ожидание берётся из AE и R.
