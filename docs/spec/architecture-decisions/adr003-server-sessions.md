# ADR003. Серверные сессии

- **Статус:** `accepted`.
- **Связанные KTD:** KTD8.
- **Связанные требования и примеры:** R1–R3; отдельного AE для аутентификации в мастер-плане нет.
- **Источник решения:** [мастер-план](../plans/2026-10-31-001-feat-campus-rating-mvp-plan.md#key-technical-decisions).

## Контекст

Студенты и преподаватели регистрируются по email и паролю. Все страницы, кроме входа, регистрации и подтверждения email, требуют входа; права зависят от роли. Фронт и API отдаются с одного origin через nginx.

## Решение

Используются серверная сессия в HttpOnly-cookie и CSRF-токен. Пароли хешируются BCrypt. В принятой конфигурации сессии хранятся в памяти backend; для нескольких инстансов KTD8 предусматривает Spring Session JDBC.

## Последствия

### Положительные

- Секрет сессии не хранится в `localStorage` и не может быть прочитан оттуда через XSS; это не означает устранения всех последствий XSS.
- Сессию можно отозвать; схема обновления токенов не требуется.

### Отрицательные

- После рестарта backend пользователи входят заново, поскольку сессии живут в памяти.
- При переходе к нескольким инстансам понадобится Spring Session JDBC.
- Cookie-аутентификация в выбранном решении требует CSRF-токена наряду с сессией.

## Рассмотренные альтернативы

KTD8 сопоставляет решение с хранением токенов в `localStorage` и схемой их обновления: серверная сессия устраняет указанную цену и позволяет отзыв. Другие варианты аутентификации мастер-план не фиксирует.

## Проверка

В мастер-U5 предусмотрены проверки регистрации, входа демо-пользователей, завершения сессии при выходе, запрета чужих ролей и CSRF. R3 задаёт границу доступа без входа. Отдельного AE нет; эти проверки относятся к будущей реализации, а не к выполнению U6 обвязки.

## Замена решения

По KTD16 новый ADR получает статус `supersedes ADR003`; в том же PR меняется KTD8 мастер-плана. Этот документ сохраняется со статусом `superseded by ADRxxx`, индекс обновляется.
