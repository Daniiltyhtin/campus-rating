# ADR004. API contract-first

- **Статус:** `accepted`.
- **Связанные KTD:** KTD9.
- **Связанные требования и примеры:** R1–R23 — область базового контракта мастер-U3; самостоятельного AE для порядка разработки API нет.
- **Источник решения:** [мастер-план](../plans/2026-10-31-001-feat-campus-rating-mvp-plan.md#key-technical-decisions).

## Контекст

Фронтенд должен разрабатывать экраны до готовности backend. Для этого нужен единый контракт, с которым сверяются типы фронтенда и фактический API backend.

## Решение

Владелец контракта — `docs/spec/api/openapi.yaml`. Каждый юнит сначала расширяет контракт, затем реализует его. Ошибки имеют формат RFC 7807 `ProblemDetail`.

Фронтенд генерирует типы через `openapi-typescript` и работает против моков MSW. Backend проверяется тестом совместимости springdoc-вывода с контрактом. Инструмент проверки выбирается в мастер-U3; `openapi-diff` указан только как кандидат.

## Последствия

### Положительные

- Экраны можно разрабатывать против MSW до реализации backend.
- Генерируемые типы и проверка совместимости связывают обе стороны API с одним контрактом.
- Общий формат ошибок задаётся до реализации обработчиков.

### Отрицательные

- Изменение API требует сначала правки контракта, затем согласования реализации, генерируемых типов и моков.
- Нужно поддерживать проверку совместимости springdoc с контрактом; её инструмент ещё предстоит выбрать в мастер-U3.

## Рассмотренные альтернативы

Мастер-план не фиксирует рассмотренные альтернативы contract-first. `openapi-diff` — кандидат для проверки совместимости, а не окончательно выбранный инструмент.

## Проверка

Verification Contract мастера требует `npm --prefix frontend run api:gen` и пустой `git diff` при изменении `openapi.yaml`. KTD9 требует тест совместимости springdoc-вывода с контрактом. Эти ворота относятся к будущей реализации API; в U6 обвязки API и типы не меняются.
