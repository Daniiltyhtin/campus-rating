# ADR008. Режимы запуска и почта

- **Статус:** `accepted`.
- **Связанные KTD:** KTD22.
- **Связанные требования и примеры:** R4, R39, R47, R48; отдельного AE в мастер-плане нет.
- **Источник решения:** [мастер-план](../plans/2026-10-31-001-feat-campus-rating-mvp-plan.md#key-technical-decisions).

## Контекст

ТЗ требует запуск `docker compose up` с синтетическими данными. Команда хочет показать демо на сервере. Ревью безопасности UX-карты (U21a) нашло две проблемы: Mailpit — общий почтовый ящик, и на открытом стенде любой перехватит чужие ссылки подтверждения и установки пароля; режим данных и срок их хранения не определены.

## Решение

- Профиль `demo` (по умолчанию в `docker-compose.yml`): контекст Liquibase `demo`, `spring.liquibase.drop-first`, очистка тома файлов при старте. Каждый запуск даёт чистый синтетический стенд; всё, созданное поверх сида, исчезает. Сброса по расписанию нет.
- Профиль `prod`: без демо-данных, без удаления, данные сохраняются.
- Почта — `spring.mail.*` из окружения, только SMTP-провайдер с отправкой от домена команды; SPF, DKIM и DMARC в DNS через Cloudflare. Mailpit не используется нигде.
- Подтверждение email — настройка `campus.mail.email-verification`: `required` или `off`, без значения по умолчанию. Backend не стартует, если её нет, и если `required` задан без `spring.mail.host`. `off` допустим в любом профиле, в том числе `prod`: решение принимается явно.
- `docker-compose.yml` явно задаёт `off`: жюри запускает стенд без SMTP-ключей, аккаунт активен сразу, импортированный студент задаёт пароль сам на форме регистрации по email из импорта, на форме регистрации видна пометка. `docker-compose.server.yml` задаёт `required` и SMTP.

## Последствия

### Положительные

- Данные посетителей демо-стенда живут до следующего перезапуска; реальные персональные данные не накапливаются.
- На сервере нет общего почтового ящика; жюри получает письма на свою почту.
- Нет общего почтового ящика ни на одном стенде.
- Выключение подтверждения видно в compose и на форме регистрации и не включается по умолчанию: опечатка или пропущенная переменная останавливает старт, а не открывает вход без проверки.

### Отрицательные

- Ошибка профиля на проде стирает данные: `drop-first` включается только в `demo`, серверный override задаёт профиль явно, тест конфигурации это проверяет (U22).
- Нужны домен, провайдер отправки и DNS-записи — это внешняя зависимость.
- Перезапуск стенда в профиле `demo` удаляет данные, созданные во время показа.
- При `off` владение email не проверяется: любой, кто знает email импортированного студента, может первым задать ему пароль. Это и есть смысл выключенного подтверждения, поэтому `off` только явный.
- Локально модуль подтверждения email виден только в выключенном виде; полностью его показывает сервер.
- Тесты читают письма из GreenMail: внутри JVM в интеграционных тестах и контейнером только в `docker-compose.e2e.yml`.

## Рассмотренные альтернативы

- Mailpit на сервере за паролем или SSH-туннелем — отклонено: жюри не сможет зарегистрироваться самостоятельно.
- Mailpit локально и в e2e — отклонено командой: лишний сервис и общий ящик; достаточно явного `off` и GreenMail в тестах.
- Неявный обход «нет SMTP — подтверждение выключено» — отклонено: пропущенная переменная на сервере молча открывала бы вход без подтверждения.
- Сброс демо-стенда по расписанию — отклонено командой: достаточно сброса при запуске и ручного удаления после хакатона.

## Проверка

Тесты U2 (повторный запуск в `demo` даёт только сид), U7 (очистка тома в `demo`), U2 (`MailModeConfigTest`: старт без настройки, `required` без SMTP отклоняются, `off` в `prod` стартует), U22 (`RunModeConfigTest`, override задаёт `required`, доставка письма с проходящими SPF и DKIM). Это запланированные проверки, а не выполненные.
