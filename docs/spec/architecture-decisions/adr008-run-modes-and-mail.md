# ADR008. Режимы запуска и почта

- **Статус:** `accepted`.
- **Связанные KTD:** KTD22.
- **Связанные требования и примеры:** R4, R39, R47, R48; отдельного AE в мастер-плане нет.
- **Источник решения:** [мастер-план](../plans/2026-10-31-001-feat-campus-rating-mvp-plan.md#key-technical-decisions).

## Контекст

ТЗ требует запуск `docker compose up` с синтетическими данными. Команда хочет показать демо на сервере. Ревью безопасности UX-карты (U21a) нашло две проблемы: Mailpit — общий почтовый ящик, и на открытом стенде любой перехватит чужие ссылки подтверждения и установки пароля; режим данных и срок их хранения не определены.

## Решение

- Профиль `demo` (по умолчанию в `docker-compose.yml`): контекст Liquibase `demo`, `spring.liquibase.drop-first`, очистка тома файлов при старте. Каждый запуск даёт чистый синтетический стенд; всё, созданное поверх сида, исчезает. Сброса по расписанию нет.
- Профиль `prod`: без демо-данных, без удаления, данные сохраняются.
- Почта — `spring.mail.*` из окружения. Локально — Mailpit. На сервере (`docker-compose.server.yml`) — SMTP-провайдер с отправкой от домена команды; SPF, DKIM и DMARC в DNS через Cloudflare; Mailpit не объявлен.

## Последствия

### Положительные

- Данные посетителей демо-стенда живут до следующего перезапуска; реальные персональные данные не накапливаются.
- На сервере нет общего почтового ящика; жюри получает письма на свою почту.
- e2e и локальная разработка по-прежнему читают письма из Mailpit.

### Отрицательные

- Ошибка профиля на проде стирает данные: `drop-first` включается только в `demo`, серверный override задаёт профиль явно, тест конфигурации это проверяет (U22).
- Нужны домен, провайдер отправки и DNS-записи — это внешняя зависимость.
- Перезапуск стенда в профиле `demo` удаляет данные, созданные во время показа.

## Рассмотренные альтернативы

- Mailpit на сервере за паролем или SSH-туннелем — отклонено: жюри не сможет зарегистрироваться самостоятельно.
- Сброс демо-стенда по расписанию — отклонено командой: достаточно сброса при запуске и ручного удаления после хакатона.

## Проверка

Тесты U2 (повторный запуск в `demo` даёт только сид), U7 (очистка тома в `demo`), U22 (`RunModeConfigTest`, конфигурация override без Mailpit, доставка письма с проходящими SPF и DKIM). Это запланированные проверки, а не выполненные.

## Замена решения

По KTD16 изменение оформляется новым ADR со статусом `supersedes ADR008` и правкой KTD22 в том же PR. Этот ADR сохраняется со статусом `superseded by ADRyyy`, индекс обновляется. ADR не меняет требования самостоятельно.
