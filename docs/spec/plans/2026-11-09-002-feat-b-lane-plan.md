## U3b. Типы, клиент, MSW и совместимость

**Контракт исполнения:** локальный U7 плана U3; R9, R10; KTD13, KTD14, KTD16. Перечень `Files` — из этого U7; дополнительных продуктовых операций нет.

### Решение проблемы KTD14 — предложение

Исходная проба `openapi-diff-core:2.1.7` дала 7 тестов, 3 failures: для OpenAPI 3.1 незаметны смена типа свойства ответа, добавление `null` и расширение `oneOf`. Контроль на OpenAPI 3.0.3 обнаруживает смену типа. По действующему KTD14 реализация остановлена.

Кандидат — `oasdiff 1.37.0`: исполняемый файл из официального release, SHA-256 сверяется с `checksums.txt`. Изолированная проба `breaking --format json --fail-on WARN` дала 9/9:

- неизменный документ и совместимое добавление необязательного свойства запроса — код 0;
- смена типа свойства ответа, nullable-ответ, расширение `oneOf` ответа, потеря обязательности свойства ответа — код 1;
- добавление обязательного свойства запроса, в том числе multipart, и переименование обязательного свойства ответа — код 1.

Источники кандидата: [поддержка OpenAPI 3.1](https://github.com/oasdiff/oasdiff/blob/main/docs/OPENAPI-31.md), [release v1.37.0](https://github.com/oasdiff/oasdiff/releases/tag/v1.37.0). Проба — `backend/target/oasdiff-probe/probe.mjs`, результат — `run.log` рядом; это временные артефакты, не часть исходников проекта.

Перед реализацией — отдельная правка KTD14, источников, рисков и `Files` плана U3 с независимым ревью. В ней нужно зафиксировать установку закреплённого бинарника для Windows и Linux, проверку SHA-256, одинаковый запуск локально и в CI и отказ проверки, если инструмент недоступен. Пропуск проверки по отсутствию инструмента запрещён. Для установщика допускается явно перечисленный вспомогательный файл; его точный путь фиксируется в этой правке.

### Порядок

1. После принятия способа сравнения закрепить отрицательные пробы в тестах инструмента. Сначала проверить неизменный документ, затем несовместимые мутации и совместимое изменение; успешный результат инструмента не должен означать отсутствие реально выполненного сравнения.
2. `api:gen`: `schema.d.ts` и разыменованные `examples.generated.ts` генерируются из одного контракта, без ручной правки. Повторный запуск не меняет файлы.
3. Типизированный клиент `openapi-fetch`: cookie-сессия, CSRF на POST/PUT/PATCH/DELETE, обновление токена по контракту, multipart через `FormData`, `Problem` как типизированная ошибка с расширениями.
4. MSW в Vitest и браузере: примеры из сгенерированного модуля, две страницы курсорного списка без дублей, изменяющие операции возвращают пример результата. Worker запускается до рендера только по явному dev-флагу.
5. `ContractCompatibilityIT`: получить `/v3/api-docs`, проверить все операции вывода на наличие в контракте, все `implemented` — на наличие в выводе. Сравнивать параметры, тела запросов и успешные ответы пересечения; planned-операции не требовать от сервера. Два независимых условия наличия нельзя заменить сравнением только `operationId`.
6. Multipart `submitAssignment`: явно зафиксировать сравнение ограничений «ровно link или file». Любое исключение из сравнения должно быть узким, документированным и проверенным; общий пропуск request body недопустим.
7. CI: линтер OpenAPI и воспроизводимость генерации в `frontend`; контрактный IT в `backend verify`. Проверка генерации обнаруживает и изменённые, и отсутствующие генерируемые файлы.

## Backend U5. Регистрация, вход и доступ

**Источники:** мастер-U5, R1–R3, R8, R49 (обязательная смена), R50; KTD8, KTD17, KTD22, KTD23; схемы auth в OpenAPI, разделы `CurrentUser`, `TeacherScope`, `GroupMembers` в швах. Продуктовые правила берутся из них без изменений.

**Files:** `backend/src/main/java/ru/campusrating/identity/`, новые changeset'ы `db/changelog/identity/` и `demo/`, тесты `backend/src/test/java/ru/campusrating/identity/`. Вспомогательные подключения Spring Security в `backend/pom.xml`, `x-status` операций auth и тестовый двойник `LedgerApi` перечисляются в отдельном готовом плане U5 до реализации. Фронтенд auth в это поручение не входит.

### Порядок

1. Подготовить отдельный implementation-ready план backend U5 по актуальным слитым U4 и U6; точные миграции, классы, независимые тесты и проверки включить в `Files`. Проверить расхождения текстовых маршрутов мастера с OpenAPI: контрактный HTTP-маршрут смены — `/api/v1/auth/password`; UI-маршрут не становится вторым API.
2. Отдельная сессия `write-tests` пишет приёмочные тесты до реализации. Зафиксировать red и причину. Реализация только после получения тестов; не запускать отдельную сессию или субагента без просьбы человека.
3. Сначала чистые типы и правило `TeacherScope`: четыре вида выдачи, допустимые сочетания полей, курс по московскому учебному году. Источник базового доступа — подтверждённый допуск, не выбранная пользователем кафедра.
4. Расширить базовые таблицы U4 новыми changeset'ами; хранить BCrypt-хеш. Добавить список преподавателей, допуск и выдачи; проверять внешние ссылки через `DirectoryApi`, не импортировать `directory.internal`.
5. Регистрация студента — одна транзакция: пользователь, членство, `MembershipActivated`, последний шаг — `LedgerApi.post` с ключом `initial:{studentId}`. После сбоя ни пользователя, ни членства, ни проводки не остаётся. Успех даёт 1000 АР ровно один раз.
6. Регистрация преподавателя и вход — по контракту; при `off` нет автодопуска даже для email из списка. Регистрация не создаёт сессию. Повторный email и email из списка при студенческой регистрации возвращают контрактные ошибки с нужным порядком проверок.
7. `SecurityConfig`, серверные сессии, CSRF, `CurrentUser`, смена пароля и отзыв остальных сессий. Для будущих операций смежных модулей проверить правила на тестовых контроллерах, не добавляя production-заглушек. `/api/v1/admin/**` доступен только ADMIN, включая существующую сверку U6.
8. Реализовать `TeacherScope`, `GroupMembers`, `MembershipActivated` в точности по швам. Без допуска доступных групп нет; потеря доступа не подменяет проверку авторства существующего ресурса у его владельца.
9. Идемпотентный demo-сид пользователей с балансами через `LedgerApi`; первый prod-администратор по R50 с обязательной сменой пароля, повторный старт без второго администратора. Применённые changeset'ы U4/U6 не править.
