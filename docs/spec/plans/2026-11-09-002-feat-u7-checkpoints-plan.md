# U7 Контрольные точки и сдача - Plan

## Goal Capsule

- **Цель.** Полный цикл точки без автоштрафа: преподаватель создаёт точку и правит её текст, студенты групп получают назначения, сдают ссылкой или файлом, преподаватель принимает пачкой или возвращает с комментарием. Все версии сдач хранятся и видны владельцу, автору точки и администратору. Блок штрафа в ответе считается уже здесь; списания пишет мастер-U8.
- **Иерархия источников.** Мастер-план (раздел U7; R3, R7, R10, R12, R14–R16, R24, R47; AE1–AE3, AE11; KTD4, KTD5, KTD7, KTD11, KTD12, KTD22, KTD23), `docs/spec/api/module-seams.md` (правила, протокол транзакции начисления, разделы 2–7), `docs/spec/api/openapi.yaml` (11 существующих операций точек и назначений и 2 новые из U1 — таблица «Операции»; схемы `Penalty`, `Assignment`), ADR002, ADR005, ADR007. Здесь R, П, Г, К, KTD и U — локальные, ссылки на мастер помечены «мастер-».
- **Профиль исполнения.** U1 — правка спеки, пишет Claude, ревьюит второй разработчик. U2–U6 пишет Codex test-first, Claude ревьюит и сам гоняет `*IT` с Docker. U7 (экраны) — отдельный PR после мастер-U21c и U3b.
- **Остановись и спроси, если:**
  - нужно изменить сигнатуру `module-seams.md` или контракт сверх U1;
  - тест зеленеет только ценой нарушения мастер-KTD5 (баланс раньше назначения) или записи мимо `LedgerApi`;
  - правило статуса в SQL расходится с чистой функцией (KTD4).
- **Ветки и PR.**
  - `u7a-checkpoint-plan` — этот план и U1 (спека), PR U7a.
  - `u7b-domain` — U2, от `main`, не ждёт мастер-U5, PR U7b.
  - `u7-checkpoints` — U3–U6, после слияния PR U7b и PR U5a (интерфейсы `CurrentUser`, `TeacherScope`, `GroupMembers`, `MembershipActivated`), PR U7.
  - `u7c-tasks-ui` — U7, после мастер-U21c и U3b.

## Product Contract

### Summary

Модуль `checkpoint`: точки, назначения и версии сдач; переходы состояний и блок штрафа — чистые функции в `checkpoint.domain`; файлы — через порт `FileStorage` на томе. Шов `StudentAssignments` для мастер-U10. Экраны студента и преподавателя — отдельным PR.

### Термины

| Термин | Значение |
|---|---|
| АР | Академический рейтинг студента, целое число 0…1000 (ограничение в базе журнала, ниже 0 не бывает); читается через `LedgerApi.balances` |
| Шаг штрафа (`step`) | Номинальная сумма одного списания в АР, целое > 0; копируется в точку при создании (по умолчанию 20) |
| Членство студента | У студента ровно одно членство в одной группе (`ACTIVE` или `PENDING`); в двух группах одновременно студент не состоит, поэтому у назначения одна группа |
| Студент-владелец | Студент, которому выдано назначение (`assignment.student_id` = id вошедшего) |
| Допущенный преподаватель | Пользователь с ролью `TEACHER` и допуском (`TeacherApproval`, мастер-KTD23). Без допуска `TeacherScope.accessibleGroupIds` пуст, поэтому любая группа для него недоступна |
| Доступная группа | Группа из `TeacherScope.accessibleGroupIds(teacherId)`: группы факультета кафедры и выданные (мастер-KTD23) |
| Автор точки | Преподаватель, создавший точку (`checkpoint.author_id`) |
| Состояние назначения | Хранимое: `OPEN` (не сдано или возвращено), `SUBMITTED` (сдано), `ACCEPTED` (принято) |
| Статус назначения | Вычисляемый для показа (П6): `IN_PROGRESS`, `OVERDUE`, `SUBMITTED`, `ACCEPTED`. `SUBMITTED` и `ACCEPTED` совпадают по имени с состояниями; `IN_PROGRESS` и `OVERDUE` — два статуса состояния `OPEN`. Переходы и ошибка `INVALID_STATE` проверяются только по состоянию. API отдаёт коды (`IN_PROGRESS`…); русские названия «В процессе», «Просрочено», «Сдано на проверку», «Принято» — подписи на экране |
| Стоимость точки | Максимум АР, который можно списать с одного студента по точке. В точке и задаче поле называется `cost`, в блоке штрафа — `cap`; значение одно и то же. В правилах ниже — `cost` |
| Слот штрафа | Отрезок времени длиной в интервал точки после дедлайна. Слот k начинается в `deadline + k × interval`; слот 0 — сам момент дедлайна, но слот идёт, только когда `now > deadline`. Номер текущего слота при `now > deadline` — `floor((now − deadline) / interval)`; следующий слот — текущий + 1 (ADR002) |
| Фаза штрафа (`phase`) | Состояние блока штрафа в ответе: `BEFORE_DEADLINE`, `RUNNING`, `ZERO_BALANCE`, `CAP_REACHED`, `STOPPED`; правило выбора — П14 |
| `minPenaltyInterval` | `2 × penaltyPollPeriod` из `SettingsApi`; при значении по умолчанию poll-period 1 с — 2 секунды (мастер-KTD4) |
| Версия сдачи | Одна сдача (ссылка или файл) с временем; новая сдача создаёт новую версию, прежние сохраняются. Если версию вернули, у неё сохраняются комментарий и время возврата |
| Материалы сдачи | Все версии сдачи назначения: ссылки, файлы с исходными именами, время сдачи и комментарии возврата. Экран администратора с этим названием открывает материалы одного назначения (`/admin/submissions/:assignmentId`) |

### Операции

Все пути — от `/api/v1`. Ошибки — `application/problem+json` с полем `code` (обработчик мастер-U4). Полные схемы — `openapi.yaml`.

| Операция | Метод и путь | Запрос | Ответ | Кто |
|---|---|---|---|---|
| `listMyCheckpoints` | `GET /checkpoints` | — | `200 {items: Checkpoint[]}`, весь список | `TEACHER`, свои точки |
| `createCheckpoint` | `POST /checkpoints` | JSON `{title, description, groupIds[], deadline, cost}` | `201 Checkpoint` | `TEACHER` |
| `getCheckpointDefaults` | `GET /checkpoints/defaults` | — | `200 {penaltyStep, penaltyIntervalSeconds, minPenaltyIntervalSeconds}` | `TEACHER` |
| `getCheckpoint` | `GET /checkpoints/{checkpointId}` | — | `200 Checkpoint` | автор; `ADMIN` |
| `updateCheckpoint` (U1) | `PATCH /checkpoints/{checkpointId}` | JSON `{title?, description?}` | `200 Checkpoint` | автор |
| `listCheckpointAssignments` | `GET /checkpoints/{checkpointId}/assignments` | query `status?` (`IN_PROGRESS`, `SUBMITTED`, `OVERDUE` или `ACCEPTED` — только статусы, не состояния), `groupId?`, `cursor?`, `limit?` (по умолчанию 20, 1…100) | `200 {items, nextCursor, statusCounts}`; строка — `{assignmentId, student {id, fullName}, group {id, name}, state, status, charged, submittedAt, submissionKind}` (`submissionKind` — `LINK`, `FILE` или `null`); `statusCounts` — объект `{IN_PROGRESS, SUBMITTED, OVERDUE, ACCEPTED}` с целыми | автор; `ADMIN` |
| `acceptAssignments` | `POST /checkpoints/{checkpointId}/assignments/accept` | JSON `{assignmentIds: [id…]}` | `200 {accepted: [id…], skipped: [{assignmentId, code: "INVALID_STATE"}]}` | автор |
| `listMyAssignments` | `GET /me/assignments` | query `view` обязателен: `active` — `OPEN` и `SUBMITTED` целиком, без страниц (`nextCursor` всегда `null`), порядок: `OVERDUE` первыми, затем по дедлайну, затем по id; `completed` — `ACCEPTED`, `cursor?`, `limit?` (20, 1…100), порядок `(acceptedAt desc, id desc)`; без `view` — `400` | `200 {items: StudentTask[], nextCursor, membershipState}`; задача — `{assignmentId, checkpoint, teacher, deadline, cost, state, status, penalty, acceptedAt}`; `membershipState` — `ACTIVE` или `PENDING` | `STUDENT` |
| `getAssignment` | `GET /assignments/{assignmentId}` | — | `200 Assignment` (с `penalty`, `returnComment`, `submission`, `submissions`) | владелец; автор; `ADMIN` |
| `submitAssignment` | `POST /assignments/{assignmentId}/submission` | `multipart/form-data`: ровно одна часть — `link` (текст) или `file` | `200 Assignment` в `SUBMITTED` | владелец |
| `returnAssignment` | `POST /assignments/{assignmentId}/return` | JSON `{comment}` | `200 Assignment` в `OPEN` | автор |
| `downloadSubmissionFile` | `GET /assignments/{assignmentId}/submission/file` | — | `200` файл последней версии | владелец; автор; `ADMIN` |
| `downloadSubmissionVersionFile` (U1) | `GET /assignments/{assignmentId}/submissions/{submissionId}/file` | — | `200` файл версии | владелец; автор; `ADMIN` |

Курсор — непрозрачная строка из `nextCursor` предыдущей страницы. Курсор, который не разбирается, или курсор от другого списка или фильтра — `400` по полю `cursor`.

### Правила

| № | Правило | Источник |
|---|---|---|
| П1 | Точку создаёт допущенный преподаватель; каждая группа — из доступных (`TeacherScope.requireAccessible`), иначе `403 GROUP_NOT_ACCESSIBLE` с названием первой недоступной | мастер-R7, KTD23, швы §3 |
| П2 | При создании: название 1…200 символов и не из одних пробелов, описание 0…10 000 (поле обязательно, пустая строка допустима), хотя бы одна группа без повторов, дедлайн строго позже текущего времени, стоимость целое 1…1000; нарушение — `400 VALIDATION_FAILED` по полю | контракт `CheckpointCreate`, `createCheckpoint` |
| П3 | Шаг и интервал штрафа копируются из `SettingsApi` при создании и больше не меняются. Если текущий интервал в настройках меньше `minPenaltyInterval`, точка не создаётся: `409 INVALID_STATE` (форма настроек мастер-U13 такой интервал не сохраняет, но настройку можно задать конфигурацией) | мастер-R7, KTD4, ADR002 |
| П4 | Назначение (точка, студент) получает студент группы точки с `ACTIVE`-членством, у которого `activatedAt` строго раньше дедлайна (`activatedAt = deadline` — назначения нет); пара (точка, студент) уникальна | мастер-R7, R16, AE11, швы §7 |
| П5 | Название и описание точки правит только её автор, в любое время. В запросе — `title` и/или `description`; отсутствующее поле не меняется; переданное проверяется как в П2; нет ни одного — `400`; любое поле, кроме `title` и `description`, — `400` по этому полю. Правка разрешена до и после дедлайна, при любых состояниях назначений. Дедлайн, стоимость, группы, шаг и интервал после создания не меняются | решение постановки |
| П6 | Состояние хранится (`OPEN`, `SUBMITTED`, `ACCEPTED`), статус вычисляется: `OPEN` и время ≤ дедлайна — «В процессе», `OPEN` и время > дедлайна — «Просрочено», `SUBMITTED` — «Сдано на проверку», `ACCEPTED` — «Принято» | мастер-KTD7, R15, контракт `AssignmentStatus` |
| П7 | Сдача — только из `OPEN`, в том числе после дедлайна; ровно одна часть: ссылка http/https до 2000 символов или файл до 10 МБ из белого списка pdf, docx, zip, png, jpg | мастер-R10, KTD12, контракт `submitAssignment` |
| П8 | Каждая сдача — новая версия; прежние версии и файлы не удаляются и не меняются | решение постановки |
| П9 | Версии сдач видят студент-владелец, автор точки и администратор; последняя версия — в поле `submission` (и после возврата, пока нет новой сдачи), все — в `submissions` от новой к старой. Файл версии отдаётся с `Content-Disposition: attachment; filename="<имя латиницей>"; filename*=UTF-8''<исходное имя в процентной кодировке>` (RFC 6266), `Content-Type` — определённый при сдаче тип; у версии-ссылки файла нет — `404` | решение постановки, мастер-R3, контракт `downloadSubmissionFile` |
| П10 | Приём — только автор точки, только из `SUBMITTED`. Клиент передаёт id в любом порядке; повторы id убираются до обработки, каждый id попадает ровно в один из списков ответа. Если хотя бы один id не принадлежит этой точке или не существует — `400` по полю `assignmentIds` для всего запроса, ничего не меняется. Остальные сервер блокирует и обрабатывает по возрастанию id: `SUBMITTED` → `ACCEPTED` (`accepted`), прочие — в `skipped` с `INVALID_STATE`. Оба списка — по возрастанию id | мастер-R14, KTD5, контракт `acceptAssignments` |
| П11 | Возврат — только автор точки, только из `SUBMITTED`, с комментарием 1…2000 символов (не из одних пробелов); назначение в `OPEN`; комментарий и время возврата сохраняются у последней версии и показываются в `returnComment` назначения, пока нет новой сдачи; после новой сдачи `returnComment` — `null`; уже списанное не обнуляется; последняя сдача остаётся в `submission` | мастер-R12, R14, AE3, контракт `returnAssignment` |
| П12 | Автор работает со своей точкой (чтение, правка текста, приём, возврат) и после потери доступа к её группам | мастер-KTD23, швы §3 |
| П13 | Администратор читает точки, назначения и сдачи; принимать, возвращать и править не может (`403`) | мастер-R24, контракт `x-roles` |
| П14 | Блок штрафа считает сервер; АР — из `LedgerApi.balances`. Фаза — по первому подходящему условию: `STOPPED` — состояние `SUBMITTED` или `ACCEPTED`, `nextAt` и `nextAmount` — `null`; `CAP_REACHED` — `charged >= cost`, оба `null`; `BEFORE_DEADLINE` — `OPEN` и время ≤ дедлайна, `nextAt` = дедлайн, `nextAmount` = `min(step, cost)`; `ZERO_BALANCE` — `OPEN`, после дедлайна, АР = 0, `nextAt` = начало слота «текущий + 1» (от `now`, не от `lastPenaltySlot`), `nextAmount` = 0; `RUNNING` — `OPEN`, после дедлайна, АР > 0, `nextAt` = начало ближайшего необработанного слота (текущий, если `lastPenaltySlot` пуст или меньше его номера, — тогда `nextAt` в прошлом; иначе текущий + 1). Пустой `lastPenaltySlot` значит «ни один слот не обработан», `nextAmount` = `min(step, cost − charged, АР)`. На стенде до мастер-U8 `charged` = 0 и `lastPenaltySlot` пуст; другие значения в примерах задаются фикстурой теста | контракт `Penalty`, ADR002, решение постановки |
| П15 | В профиле `demo` при старте база пересоздаётся из сида (`drop-first`) и том файлов очищается — вместе, поэтому версий сдач без файлов не остаётся; в `prod` ни то ни другое не делается | мастер-KTD22, R47 |

### Граничные случаи

| № | Случай | Поведение | Текст для пользователя (`detail`) |
|---|---|---|---|
| Г1 | Повторная сдача из `SUBMITTED` или `ACCEPTED` | `409 INVALID_STATE`, ничего не пишется | «Работа уже сдана» / «Работа уже принята» |
| Г2 | Файл 11 МБ | `413 FILE_TOO_LARGE` до контроллера (лимиты multipart: файл 10 МБ, запрос 11 МБ) | «Файл больше 10 МБ» |
| Г3 | Файл `.exe` или тип вне списка | `415 FILE_TYPE_NOT_ALLOWED` | «Можно pdf, docx, zip, png или jpg» |
| Г4 | Ни ссылки, ни файла; обе сразу; ссылка не http/https | `400 VALIDATION_FAILED` по полю `link` или `file` | по коду поля |
| Г5 | Возврат без комментария или из `OPEN` | `400` по полю `comment` / `409 INVALID_STATE` | «Нужен комментарий» / «Вернуть можно только сданную работу» |
| Г6 | Чужой студент открывает назначение или файл | `403 FORBIDDEN` | — |
| Г7 | Преподаватель, не автор, принимает, возвращает или правит точку | `403 FORBIDDEN`, даже если группа ему доступна | — |

## Planning Contract

### Key Technical Decisions

- KTD1. **Спека раньше кода.** U1 правит контракт, мастер-R7 и R10 и вливается до U3: сначала контракт, потом код (`AGENTS.md`). `Submission` получает `id`, `returnComment`, `returnedAt`.
  - `PATCH /api/v1/checkpoints/{checkpointId}` (`updateCheckpoint`): тело — `title` и/или `description` (хотя бы одно), ответ — `Checkpoint`; роль `TEACHER`, только автор.
  - `Assignment.submissions` — все версии от новой к старой; `Submission` получает `id`; `submission` остаётся последней версией, чтобы не ломать мастер-U10.
  - `GET /api/v1/assignments/{assignmentId}/submissions/{submissionId}/file` (`downloadSubmissionVersionFile`); доступ как у `getAssignment`. Прежняя операция `.../submission/file` — файл последней версии.
- KTD2. **Схема** (`db/changelog/checkpoint/<ts>-checkpoint.sql`).
  - `checkpoint`: `id`, `author_id` → `app_user`, `title`, `description`, `deadline timestamptz`, `cost int check (cost between 1 and 1000)`, `penalty_step int`, `penalty_interval_seconds int`, `created_at`, `updated_at`.
  - `checkpoint_group`: `(checkpoint_id, group_id)` — первичный ключ; `group_id` → `study_group`.
  - `assignment`: `id`, `checkpoint_id`, `student_id` → `app_user`, `group_id`, `student_full_name`, `state text check`, `charged int not null default 0 check (charged >= 0)`, `last_penalty_slot int null`, `accepted_at`, `created_at`; `unique (checkpoint_id, student_id)`; индексы под U8 (`state, deadline` через точку) и под таблицу точки (`checkpoint_id, student_full_name, id`).
  - `submission`: `id`, `assignment_id`, `kind text check ('LINK','FILE')`, `url` (в запросе — часть `link`, в ответе — поле `url`), `file_key`, `file_name`, `size_bytes`, `content_type`, `submitted_at`, `return_comment`, `returned_at`; индекс `(assignment_id, submitted_at desc, id desc)`. У `assignment` нет своего `return_comment`: он берётся из последней версии, пока состояние `OPEN`.
- KTD3. **ФИО и группа студента — снимок в назначении.** Таблица точки сортирует и пагинирует по `(ФИО, id)` (контракт), а ФИО живёт в `identity`. SQL-соединения с таблицами чужого модуля нет: при создании назначения ФИО и группа берутся у `GroupMembers` и пишутся в строку. Переименования пользователя в MVP нет; появится — синхронизация событием.
- KTD4. **Статус в SQL — зеркало функции.** Фильтр по статусу и `statusCounts` считаются в SQL по `state`, `deadline` и `now` из `Clock` (`OPEN` и `now <= deadline` — `IN_PROGRESS`). Чистая `AssignmentStatusPolicy` — источник правды; IT сверяет SQL и функцию на одном наборе назначений вокруг границы дедлайна.
- KTD5. **Блок штрафа — чистая функция `PenaltyView`** в `checkpoint.domain`: вход — состояние, дедлайн, стоимость, шаг, интервал, `charged`, `lastPenaltySlot`, АР, `now`; выход — схема `Penalty` по её таблице фаз. Текущий слот — `floor((now − deadline) / interval)` при `now > deadline` (ADR002). Мастер-U8 переиспользует функцию слота и пишет `charged`, `last_penalty_slot`.
- KTD6. **Порядок в транзакциях сдачи, приёма и возврата.** `SELECT … FOR UPDATE` назначений по возрастанию id → перепроверка состояния → запись (мастер-KTD5, швы «Протокол»). U7 не зовёт `LedgerApi.post`; блокировка баланса здесь не нужна.
- KTD7. **Файлы.** Порт `FileStorage` в `shared.storage`: `save(stream, meta) → key`, `open(key)`, `delete(key)`, `clear()`; реализация на томе (`campus.storage.dir`), ключ — случайный UUID без исходного имени. Файл пишется до вставки версии; при откате транзакции — удаляется (`TransactionSynchronization.afterCompletion`). Тип проверяется по расширению и сигнатуре содержимого, а не по `Content-Type` клиента. `demo` очищает том при старте (KTD22).
- KTD8. **Назначения — три пути, одно правило.** `createCheckpoint` вставляет назначения сам, в своей транзакции, до ответа `201`; слушатель `CheckpointCreated` после commit досоздаёт пропущенные (гонка с активацией); слушатель `MembershipActivated` — для новичков. Все три пути: слушатель `CheckpointCreated` и слушатель `MembershipActivated` вставляют `ON CONFLICT (checkpoint_id, student_id) DO NOTHING` и проверяют `activatedAt < deadline` (швы §7). Слушатели — `@ApplicationModuleListener`, реестр публикаций Modulith (мастер-KTD11).
- KTD10. **Контракт и код после U3b.** U3b (ветка `u3b-api-client`) добавляет генерацию и проверку совместимости:
  - любая правка `openapi.yaml` сопровождается `npm --prefix frontend run api:gen` и коммитом `frontend/src/api/schema.d.ts` и `frontend/src/mocks/examples.generated.ts`: CI `frontend` падает на непустом `git diff`. Кто из PR U7a и U3b вливается вторым, тот перезапускает `api:gen`;
  - `ContractCompatibilityIT` в `verify` сравнивает вывод springdoc с контрактом по операциям `x-status: implemented`: параметры, тела запросов, схемы 2xx, типы, `nullable`, `required`, `oneOf`, имена полей. Поэтому DTO контроллеров U4–U6 пишутся строго по схемам контракта, а `x-status: implemented` ставится в том же PR, что и контроллер;
  - по обновлённому KTD14 U3 тело `submitAssignment` (multipart, `oneOf` «ссылка или файл») сравнивается полностью: контроллер явно описывает `oneOf` через `@Schema`. Собственный IT дополнительно проверяет реальные части `link` и `file`; исключения requestBody не вводятся. Native gate реализуется отдельным PR23 после принятия этого решения.
- KTD9. **Доступ.** Роль проверяет `SecurityConfig` мастер-U5 по `x-roles`; модуль проверяет владельца: студент — `assignment.student_id`, преподаватель — `checkpoint.author_id`, администратор — только чтение. До слияния мастер-U5 `*IT` используют `@MockitoBean` `CurrentUser`, `TeacherScope`, `GroupMembers` (швы, демо-данные контракта).

  - Шов `StudentAssignments`: `active` и `completed` совпадают с HTTP-ответом по составу и статусам; материалов сдачи и комментария в типе нет.
- **Verification.** `verify`; шаги 1–14 «Как проверить» HTTP-клиентом на демо-стеке (`docker compose up`).

### U7. Экраны задач (PR U7c)

- **Goal.** Студент видит и сдаёт задачи, преподаватель создаёт точку и проверяет работы на мобильной и десктопной ширине.
- **Requirements.** П6–П14 (видимое поведение); мастер-R15, R40; UX-правила `docs/spec/ux/screen-map.md`; ADR009.
- **Dependencies.** U6; мастер-U21c (тема, шаблоны), U3b (клиент, MSW).
- **Files:** `frontend/src/features/tasks/` (мои задачи `/tasks`, задача `/tasks/:id` с блоком штрафа и историей сдач, мои точки `/checkpoints`, новая точка `/checkpoints/new`, точка `/checkpoints/:id` с фильтрами, массовым приёмом, возвратом и правкой текста); тесты `TaskList.test.tsx`, `TaskPage.test.tsx`, `CheckpointPage.test.tsx`.
- **Approach.** Пять состояний блока штрафа и тексты — из UX-правил карты экранов; обратный отсчёт до `nextAt` без формулы на клиенте; если `nextAt` уже в прошлом (списание ждёт ближайшего прохода планировщика), вместо отсчёта — «Следующее списание −N АР — в ближайшую минуту» (текст предложен, сверить с UX-правилами); итог приёма «Принято 2 из 3» без фона, выбор строки — чекбокс и линия (ADR009).
- **Test scenarios:**
  - Список: `OVERDUE` первыми; `PENDING` — текст «Членство ждёт подтверждения»; пустой — «Новых задач нет…».
  - Задача: пять фаз блока штрафа по `phase`; ошибка поля файла (Г3) у поля; история версий от новой к старой.
  - Точка: выбрать три, «Принять 3 работы» → итог «Принято 2 из 3» и причина пропуска; «Вернуть…» требует комментарий.
  - 360 и 1280 px без горизонтальной прокрутки страницы; скриншоты в PR.
- **Verification.** `npm --prefix frontend run check`; шаги 1, 4–9, 11 «Как проверить» через экраны на демо-стеке в окне 360 px.
