# U7 Контрольные точки и сдача - Plan

## Goal Capsule

- **Цель.** Полный цикл точки без автоштрафа: преподаватель создаёт точку и правит её текст, студенты групп получают назначения, сдают ссылкой или файлом, преподаватель принимает пачкой или возвращает с комментарием. Все версии сдач хранятся и видны владельцу, автору точки и администратору. Блок штрафа в ответе считается уже здесь; списания пишет мастер-U8.
- **Иерархия источников.** Мастер-план (раздел U7; R3, R7, R10, R12, R14–R16, R24, R47; AE1–AE3, AE11; KTD4, KTD5, KTD7, KTD11, KTD12, KTD22, KTD23), `docs/spec/api/module-seams.md` (правила, протокол транзакции начисления, разделы 2–7), `docs/spec/api/openapi.yaml` (11 операций точек и назначений, схемы `Penalty`, `Assignment`), ADR002, ADR005, ADR007. Здесь R, П, Г, К, KTD и U — локальные, ссылки на мастер помечены «мастер-».
- **Профиль исполнения.** U1 — правка спеки, пишет Claude, ревьюит второй разработчик. U2–U6 пишет Codex test-first, Claude ревьюит и сам гоняет `*IT` с Docker. U7 (экраны) — отдельный PR после мастер-U21c и U3b.
- **Остановись и спроси, если:**
  - нужно изменить сигнатуру `module-seams.md` или контракт сверх U1;
  - тест зеленеет только ценой нарушения мастер-KTD5 (баланс раньше назначения) или записи мимо `LedgerApi`;
  - правило статуса в SQL расходится с чистой функцией (KTD4).
- **Ветки и PR.**
  - `u7a-checkpoint-plan` — этот план и U1 (спека), PR U7a.
  - `u7-domain` — U2, от `main`, не ждёт мастер-U5.
  - `u7-checkpoints` — U3–U6, после слияния PR U5a (интерфейсы `CurrentUser`, `TeacherScope`, `GroupMembers`, `MembershipActivated`).
  - `u7c-tasks-ui` — U7, после мастер-U21c и U3b.

### Правила

| № | Правило | Источник |
|---|---|---|
| П1 | Точку создаёт допущенный преподаватель; каждая группа — из доступных (`TeacherScope.requireAccessible`), иначе `403 GROUP_NOT_ACCESSIBLE` с названием первой недоступной | мастер-R7, KTD23, швы §3 |
| П2 | Дедлайн строго в будущем, иначе `400` по полю `deadline`; стоимость 1…1000 | контракт `createCheckpoint`, `CheckpointCreate` |
| П3 | Шаг и интервал штрафа копируются из `SettingsApi` при создании и больше не меняются; интервал меньше `minPenaltyInterval` — `409 INVALID_STATE` | мастер-R7, KTD4, ADR002 |
| П4 | Назначение (точка, студент) получает студент группы точки с `ACTIVE`-членством, у которого `activatedAt` раньше дедлайна; пара уникальна | мастер-R7, R16, AE11, швы §7 |
| П5 | Название и описание точки правит только её автор, в любое время; дедлайн, стоимость, группы, шаг и интервал после создания не меняются | решение постановки |
| П6 | Состояние хранится (`OPEN`, `SUBMITTED`, `ACCEPTED`), статус вычисляется: `OPEN` и время ≤ дедлайна — «В процессе», `OPEN` и время > дедлайна — «Просрочено», `SUBMITTED` — «Сдано на проверку», `ACCEPTED` — «Принято» | мастер-KTD7, R15, контракт `AssignmentStatus` |
| П7 | Сдача — только из `OPEN`, в том числе после дедлайна; ровно одна часть: ссылка http/https до 2000 символов или файл до 10 МБ из белого списка pdf, docx, zip, png, jpg | мастер-R10, KTD12, контракт `submitAssignment` |
| П8 | Каждая сдача — новая версия; прежние версии и файлы не удаляются и не меняются | решение постановки |
| П9 | Версии сдач видят студент-владелец, автор точки и администратор; последняя версия — в поле `submission`, все — списком от новой к старой | решение постановки, мастер-R3 |
| П10 | Приём — только автор точки, только из `SUBMITTED`; пачкой по возрастанию id назначения; остальные — в `skipped` с `INVALID_STATE`; id не из этой точки — `400` для всего запроса до изменений | мастер-R14, KTD5, контракт `acceptAssignments` |
| П11 | Возврат — только автор точки, только из `SUBMITTED`, с комментарием 1…2000 символов; назначение в `OPEN`; уже списанное не обнуляется; последняя сдача остаётся видна | мастер-R12, R14, AE3, контракт `returnAssignment` |
| П12 | Автор работает со своей точкой (чтение, правка текста, приём, возврат) и после потери доступа к её группам | мастер-KTD23, швы §3 |
| П13 | Администратор читает точки, назначения и сдачи; принимать, возвращать и править не может (`403`) | мастер-R24, контракт `x-roles` |
| П14 | Блок штрафа считает сервер по таблице схемы `Penalty`; АР — из `LedgerApi.balances`; до мастер-U8 `charged` = 0 | контракт `Penalty`, решение постановки |
| П15 | В профиле `demo` том файлов очищается при старте | мастер-KTD22, R47 |

| № | Случай | Поведение | Текст для пользователя (`detail`) |
|---|---|---|---|

| Г2 | Файл 11 МБ | `413 FILE_TOO_LARGE` до контроллера (лимиты multipart заданы явно: файл 10 МБ, запрос с запасом на поля) | «Файл больше 10 МБ» |

## Planning Contract

### Key Technical Decisions

- KTD1. **Спека раньше кода.** U1 правит контракт, мастер-R7 и R10 и вливается до U3: сначала контракт, потом код (`AGENTS.md`).
  - `PATCH /api/v1/checkpoints/{checkpointId}` (`updateCheckpoint`): тело — `title` и/или `description` (хотя бы одно), ответ — `Checkpoint`; роль `TEACHER`, только автор.
  - `Assignment.submissions` — все версии от новой к старой; `Submission` получает `id`; `submission` остаётся последней версией, чтобы не ломать мастер-U10.
  - `GET /api/v1/assignments/{assignmentId}/submissions/{submissionId}/file` (`downloadSubmissionVersionFile`); доступ как у `getAssignment`. Прежняя операция `.../submission/file` — файл последней версии.
- KTD2. **Схема** (`db/changelog/checkpoint/<ts>-checkpoint.sql`).
  - `checkpoint`: `id`, `author_id` → `app_user`, `title`, `description`, `deadline timestamptz`, `cost int check (cost between 1 and 1000)`, `penalty_step int`, `penalty_interval_seconds int`, `created_at`, `updated_at`.
  - `checkpoint_group`: `(checkpoint_id, group_id)` — первичный ключ; `group_id` → `study_group`.
  - `assignment`: `id`, `checkpoint_id`, `student_id` → `app_user`, `group_id`, `student_full_name`, `state text check`, `charged int not null default 0 check (charged >= 0)`, `last_penalty_slot int null`, `return_comment text null`, `returned_at`, `accepted_at`, `created_at`; `unique (checkpoint_id, student_id)`; индексы под U8 (`state, deadline` через точку) и под таблицу точки (`checkpoint_id, student_full_name, id`).
  - `submission`: `id`, `assignment_id`, `kind text check ('LINK','FILE')`, `url`, `file_key`, `file_name`, `size_bytes`, `content_type`, `submitted_at`; индекс `(assignment_id, submitted_at desc, id desc)`.
- KTD3. **ФИО и группа студента — снимок в назначении.** Таблица точки сортирует и пагинирует по `(ФИО, id)` (контракт), а ФИО живёт в `identity`. SQL-соединения с таблицами чужого модуля нет: при создании назначения ФИО и группа берутся у `GroupMembers` и пишутся в строку. Переименования пользователя в MVP нет; появится — синхронизация событием.
- KTD4. **Статус в SQL — зеркало функции.** Фильтр по статусу и `statusCounts` считаются в SQL по `state`, `deadline` и `now` из `Clock` (`OPEN` и `now <= deadline` — `IN_PROGRESS`). Чистая `AssignmentStatusPolicy` — источник правды; IT сверяет SQL и функцию на одном наборе назначений вокруг границы дедлайна.
- KTD5. **Блок штрафа — чистая функция `PenaltyView`** в `checkpoint.domain`: вход — состояние, дедлайн, стоимость, шаг, интервал, `charged`, `lastPenaltySlot`, АР, `now`; выход — схема `Penalty` по её таблице фаз. Текущий слот — `floor((now − deadline) / interval)` при `now > deadline` (ADR002). Мастер-U8 переиспользует функцию слота и пишет `charged`, `last_penalty_slot`.
- KTD6. **Порядок в транзакциях сдачи, приёма и возврата.** `SELECT … FOR UPDATE` назначений по возрастанию id → перепроверка состояния → запись (мастер-KTD5, швы «Протокол»). U7 не зовёт `LedgerApi.post`; блокировка баланса здесь не нужна.
- KTD7. **Файлы.** Порт `FileStorage` в `shared.storage`: `save(stream, meta) → key`, `open(key)`, `delete(key)`, `clear()`; реализация на томе (`campus.storage.dir`), ключ — случайный UUID без исходного имени. Файл пишется до вставки версии; при откате транзакции — удаляется (`TransactionSynchronization.afterCompletion`). Тип проверяется по расширению и сигнатуре содержимого, а не по `Content-Type` клиента. `demo` очищает том при старте (KTD22).
- KTD8. **Назначения — три пути, одно правило.** Создание точки, слушатель `CheckpointCreated` и слушатель `MembershipActivated` вставляют `ON CONFLICT (checkpoint_id, student_id) DO NOTHING` и проверяют `activatedAt < deadline` (швы §7). Слушатели — `@ApplicationModuleListener`, реестр публикаций Modulith (мастер-KTD11).
- KTD9. **Доступ.** Роль проверяет `SecurityConfig` мастер-U5 по `x-roles`; модуль проверяет владельца: студент — `assignment.student_id`, преподаватель — `checkpoint.author_id`, администратор — только чтение. До слияния мастер-U5 `*IT` используют `@MockitoBean` `CurrentUser`, `TeacherScope`, `GroupMembers` (швы, демо-данные контракта).

## Implementation Units

### U1. Спека: правка точки и версии сдач (PR U7a)

- **Goal.** Контракт и мастер-план описывают правку текста точки и историю сдач до кода.
- **Requirements.** П5, П8, П9; KTD1.
- **Dependencies.** нет.
- **Files:** `docs/spec/api/openapi.yaml` (операции и схемы KTD1, примеры, `x-status: planned`), `docs/spec/api/README.md` (матрица сценариев), мастер-план (R7 — правка названия и описания автором; R10 — версии сдач и кто их видит), `docs/spec/glossary.md` («Версия сдачи»).
- **Test scenarios:** линтер контракта зелёный; примеры `Assignment` содержат две версии; `check-agent-docs` проходит.
- **Verification.** Ревью второго разработчика как потребителя (мастер-U10 читает `Assignment` и `StudentAssignments`).

### U2. Домен: состояния, статус, блок штрафа

- **Goal.** Все правила состояния и штрафа — чистые функции с полным покрытием.
- **Requirements.** П6, П7 (переходы), П10, П11 (переходы), П14; KTD4, KTD5.
- **Dependencies.** U1 не нужен: контракт `Penalty` уже есть.
- **Files:** `backend/src/main/java/ru/campusrating/checkpoint/AssignmentState.java`, `AssignmentStatus.java` (корень — типы шва §6); `checkpoint/domain/AssignmentTransitions.java`, `AssignmentStatusPolicy.java`, `PenaltyView.java`, `PenaltySlot.java`, `SubmissionRules.java`; тесты в `backend/src/test/java/ru/campusrating/checkpoint/domain/`.
- **Execution note.** Test-first, сначала `AssignmentStatusPolicyTest` и `PenaltyViewTest` по примерам 1–6.
- **Test scenarios:**
  - Примеры 1–6 — по одному тесту.
  - Covers мастер-AE1. Слоты 0, 1, 2 при `now` 12:00:00.5, 12:01:01, 12:02:01; `nextAt` — начало ближайшего необработанного слота.
  - Covers мастер-AE3. После возврата в 12:05:10 с `lastPenaltySlot` 1 — `RUNNING`, ближайший слот 5, `nextAt` в прошлом (12:05:00).
  - `nextAmount` = `min(step, cap − charged, АР)`: АР 7 → 7; остаток 10 → 10.
  - Переходы: `OPEN → SUBMITTED`, `SUBMITTED → ACCEPTED`, `SUBMITTED → OPEN` разрешены; остальные — доменная ошибка `INVALID_STATE`.
