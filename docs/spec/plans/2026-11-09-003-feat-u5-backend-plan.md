# U5 Backend — регистрация, сессии и доступ

## Goal Capsule

- **Цель.** Студент регистрируется с 1000 АР, преподаватель входит без самовольного допуска; серверная сессия и CSRF ограничивают API по роли, а швы identity готовы потребителям.
- **Источники.** Мастер-U5: R1–R3, R8, R49 (смена пароля), R50; KTD8, KTD17, KTD22, KTD23; `api/openapi.yaml` (восемь операций auth), `api/module-seams.md` (CurrentUser, TeacherScope, GroupMembers, MembershipActivated), ADR003, ADR007, ADR008, глоссарий.
- **Зависимости.** Слитые U4 и U6; контракт U3a, инструменты U3b. Приёмочные тесты пишет отдельная сессия `write-tests` до production-кода; исполнитель их не меняет.
- **Ветка.** `u5-identity-backend`. Без frontend auth, администрирования допуска и подтверждения почты. Тестовый двойник LedgerApi допустим для проверки отката, обычные успешные IT используют настоящий журнал.

## Scope / Files

- `backend/src/main/java/ru/campusrating/identity/`: публичные типы и интерфейсы точно по швам; `domain/TeacherGrant.java`, `domain/TeacherAccess.java`; `internal/` — SQL, регистрация, сессии, seed/bootstrap, реализация швов и SecurityConfig; `api/` — DTO и AuthController.
- Новые Liquibase SQL в `db/changelog/identity/` и `db/changelog/demo/`; старые changeset'ы не меняются.
- `backend/pom.xml`: стартер Spring Security, тестовый security-стартер; Swagger annotations без runtime Jackson 2, если нужны для точной схемы auth DTO.
- `backend/src/test/java/ru/campusrating/identity/RegistrationIT.java`, `TeacherScopeIT.java`, `SessionSecurityIT.java`, `BootstrapAdminIT.java`, `IdentitySeamsIT.java`, тестовые support/фикстуры в том же пакете; чистые unit-тесты domain рядом в тестовом дереве.
- Смежные проверки с изменившимися HTTP-правами: `SmokeIT.java` и HTTP-часть `LedgerIT.java`. Меняются только предположения о доступе после SecurityConfig, не проверки сумм и транзакций. Никакой правки независимых приёмочных тестов этого U5.
- `docs/spec/api/openapi.yaml`: только x-status реализованных операций. Документация запуска bootstrap и журнал.

## Key Technical Decisions

### Данные

Новый changeset расширяет `app_user`: `password_hash text`, `must_change_password boolean not null default false`, `department_id bigint references department(id)`. Нельзя выдавать одинаковый пароль ранее существовавшим строкам: `password_hash` остаётся nullable для старых технических/тестовых строк U4/U6, которые не получают возможность входа. Только новый сервис identity создаёт аутентифицируемого пользователя с BCrypt-хешем; вход с NULL hash всегда INVALID_CREDENTIALS. Проверка отдельным IT. Строка без hash не превращается в доменный Credentials. Это сохраняет совместимость старых записей без обхода аутентификации.

Таблицы:

- `teacher_allowlist(email text not null, department_id bigint not null references department(id))`, уникальный индекс lower(email).
- `teacher_approval(teacher_id bigint primary key references app_user(id), approved_by bigint references app_user(id), approved_at timestamptz not null)`: единственный источник флага teacherApproved; кто и когда допустил — по мастер-KTD23. `approved_by` NULL — допуск без администратора (demo-сид, подтверждение email из списка в U15); `approved_at` — от Clock. Административное изменение — U13, здесь только чтение и demo-сид.
- `teacher_grant(id bigint generated by default as identity primary key, teacher_id bigint not null references app_user(id), kind text not null, group_id bigint references study_group(id), faculty_id bigint references faculty(id), course integer)`.

CHECK выдачи разрешает только: GROUP с group_id; FACULTY с faculty_id; FACULTY_COURSE с faculty_id и course 1…6; COURSE с course 1…6. Все остальные целевые поля NULL. В коде `TeacherGrant` — sealed interface с четырьмя record-вариантами Group, Faculty, FacultyCourse, Course; недопустимые комбинации полей не представимы. Данные из SQL проверяются при разборе.

`TeacherAccess` — чистая функция: допуск, факультет кафедры, группы справочника, типизированные выдачи и дата по Москве → множество id. Без допуска — пусто. Учебный год начинается 1 сентября; курс = учебный год − admissionYear + 1; курс вне 1…6 не соответствует выдаче курса. Базовый доступ ко всему факультету кафедры не зависит от курса группы.

### Регистрация и швы

Email сравнивается без учёта регистра; BCrypt не применяется к паролю длиннее допустимого для BCrypt количества UTF-8 байт, возвращается контрактный VALIDATION_FAILED/TOO_LONG, а не скрытая обрезка. Остальные ограничения полей — точные схемы OpenAPI.

Студент: проверка списка преподавателей раньше занятого email, затем существования и принадлежности группы факультету; одна транзакция создаёт app_user и ACTIVE-членство с activated_at от Clock, публикует MembershipActivated и последним действием вызывает LedgerApi.post(INITIAL +1000, initial:{id}, REGISTRATION, автор null). Повтор email не создаёт ни пользователя, ни проводку; исключение журнала откатывает пользователя, членство и публикацию.

Преподаватель: кафедра с формы существует, но при off не даёт допуска даже для email из списка. Регистрация не создаёт сессию, успех — 201 {userId,nextStep:LOGIN}. При required U2 пока запрещает старт до U15; этот guard не снимается и подтверждение не обходится.

CurrentUser, TeacherScope, GroupMembers и все их record-типы — точные сигнатуры module-seams. CurrentUser читает актуальные данные пользователя; изменение допуска/членства/кафедры не прячется в устаревшем principal. Подписи и группы читаются через публичный DirectoryApi. Именованные интерфейсы открываются только если нужны соседям; foreign internal не импортируется.

### HTTP и сессии

Серверная HttpOnly-cookie сессия, SameSite=Lax, BCrypt, без JWT и localStorage. Login — JSON-контроллер, сохраняющий SecurityContext в HttpSession через SecurityContextRepository и меняющий id сессии при аутентификации. Учёт активных сессий — SessionRegistry с удалением завершённых; после смены пароля все прочие сессии отзываются, включая уже существующие cookie. Один backend по ADR003, JDBC-сессии не добавляются.

SPA CSRF: CookieCsrfTokenRepository с XSRF-TOKEN / X-XSRF-TOKEN, GET /api/v1/auth/csrf материализует токен и отвечает 204. После login/logout/password клиент получает свежий токен. Не отключать CSRF ни для login, ни для регистрации. Multipart будущего U7 использует тот же заголовок.

Публичны только чтение справочников, auth/config, auth/csrf, POST login и register/student|teacher; health остаётся доступным для локального compose healthcheck. Logout, me и password требуют сессию. Остальные /api/v1 требуют входа; `/api/v1/admin/**` — ADMIN. Ролевые границы ресурсов — из x-roles контракта, владение проверяет модуль-владелец. Материалы сдачи допускают роли STUDENT/TEACHER/ADMIN, но доступ к конкретной сдаче остаётся у checkpoint.

До смены обязательного пароля допустимы только auth/me, auth/csrf, auth/logout и auth/password. Фильтр возвращает 403 PASSWORD_CHANGE_REQUIRED до вызова остальных контроллеров. Неверная роль — FORBIDDEN, гость — UNAUTHENTICATED, отсутствие/неверный CSRF — CSRF_INVALID. Формат application/problem+json создаётся через Jackson 3; нельзя передавать ProblemDetail в Jackson 2 writer и получать вложенный properties вместо верхнего code.

Auth DTO отражают точные схемы OpenAPI: CurrentStudent, CurrentTeacher, CurrentAdmin с discriminated role, RegistrationResult, AuthConfig. Смена пароля — POST /api/v1/auth/password, currentPassword/newPassword; не создавать второй API /password/change из текстового примера UI. После смены старый пароль не работает, текущая сессия остаётся, остальные получают 401.

### Bootstrap и demo

Prod bootstrap использует CAMPUS_BOOTSTRAP_ADMIN_EMAIL/PASSWORD только если ADMIN ещё нет; не хранить пароль в файлах и не выводить его в лог. Первый ADMIN требует смены; повторный старт не меняет его пароль и не создаёт второго.

Demo-пользователи и список преподавателей — синтетические данные примеров контракта, ids 1001…1004, 2001…2002, 3001. Demo teacher 2001 допущен, 2002 нет. Начальные балансы demo-студентов — только через LedgerApi в транзакции seed, SQL в ledger из identity запрещён. Факультеты и группы уже создаёт U4. Повтор seed без пересоздания схемы идемпотентен; общий demo-профиль всё равно пересоздаёт данные по R47. Тестовые фикстуры не включают demo-контекст в общей PostgresIntegrationTest-базе.

## Implementation Units

### Приёмочные тесты до реализации

Отдельная сессия пишет HTTP/SQL/шовные тесты по матрице ниже, выполняет red и фиксирует причину. Может добавлять test-only контроллеры в security-срезе; они не становятся production API и не попадают в общий ContractCompatibilityIT. Пользовательский сценарий сессии проверяется настоящими cookie и отдельными HttpClient/CookieManager, а не только mock principal.

### Чистое правило доступа и типы

Перенести публичные типы швов, затем test-first реализовать sealed TeacherGrant и TeacherAccess. Unit-тесты всех четырёх выдач, объединения, отсутствия допуска и границ учебного года.

### Схема, регистрация и чтение identity

Добавить миграции и SQL-репозиторий на JdbcClient, реализовать транзакцию регистрации, швы и событие. Проверить rollback с отказом LedgerApi и успех с настоящим журналом. Не писать main-заглушки других модулей.

### Аутентификация, CSRF и обязательная смена

Добавить SecurityConfig, JSON login/logout/me/config/csrf/password, актуальный CurrentUser и отзыв сессий. Проверить всю матрицу ролей и эндпоинт сверки, затем закрыть старые HTTP-тесты, изменившиеся после включения безопасности.

### Seed/bootstrap и контракт

Добавить demo seed и prod bootstrap, проверить реальный запуск, отметить x-status восьми auth-операций, прогнать ContractCompatibilityIT и полный verify. Не менять DTO только ради выключения проверки: расхождение исправляется настоящим типом или явной точной схемой.
