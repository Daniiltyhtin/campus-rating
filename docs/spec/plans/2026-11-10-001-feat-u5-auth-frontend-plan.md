# U5 frontend — вход, регистрация и смена пароля

## Goal Capsule

- **Цель.** Вместо заглушки гость входит и регистрируется; существующая cookie-сессия восстанавливается после перезагрузки. Временный пароль требует смены до открытия разделов. Выход завершает сессию.
- **Источники.** Мастер-U5, R1–R3, R8, R49–R50, R47–R48; KTD8, KTD17, KTD22–KTD23; ADR003, ADR007–ADR009; `docs/spec/ux/screen-map.md`, glossary; восемь auth-операций и три directory-операции `docs/spec/api/openapi.yaml`.
- **База.** `origin/main` на `8d53b36`: backend U5 и тема U21c приняты в PR24/25. Контракт и backend не меняются. Реализация не включает продуктовые задачи, профиль, активности, администрирование и отправку писем U15.
- **Исполнение.** Ветка `u5-auth-frontend`. Отдельный tester, явно разрешённый человеком в сессии, пишет приёмочные UI-тесты до production-кода. Исполнитель их не меняет. Коммит, пуш ветки и создание PR разрешены отдельным поручением человека 11 ноября; независимая приёмка отдельным ревьюером.

## Files

- `frontend/src/features/auth/`: страницы LoginPage, RegisterPage, ChangePasswordPage, общий AuthLayout, формы, auth-query/mutations, проверка полей и тексты ошибок, стили на токенах; `*.acceptance.test.tsx` — только tester.
- `frontend/src/app/session.ts`, `router.tsx`, `routeElements.tsx`, `AppShell.tsx`, `navigation.ts` и их существующие тесты: подключение серверной сессии, охранник, меню пользователя/выход и уведомление о допуске.
- `frontend/src/main.tsx`, `frontend/src/test/render.tsx`: общие провайдеры и единая настройка QueryClient; тестовые fixtures auth в `frontend/src/test/`.
- Вспомогательный `frontend/vite.config.ts`: ограничение числа одновременно работающих jsdom-воркеров для воспроизводимых проверок расширенного UI-набора, без ослабления ожиданий.
- `frontend/src/api/client.ts` и `client.test.ts`: сохранение и проверка fieldErrors в типизированном ValidationProblem, обработка истечения сессии/обязательной смены через слой auth. Генерируемые типы не редактируются.
- `frontend/src/mocks/auth.ts`, `handlers.ts` и auth-тесты: изолируемая cookie-сессия для dev-демо, исходные пользователи и ответы из generated examples; существующие generic contract mocks сохраняются.
- `docs/reviews/u5-auth/`: скриншоты и отчёт реальных проверок; этот план, журнал, уроки в `frontend/AGENTS.md` при необходимости.

## Поведение и границы

1. **Сессия (R3, KTD8).** Источник данных — TanStack Query `GET /auth/me`; 401 означает гостя, сеть/500 — ошибку с «Повторить», а не гостя. При старте материализовать CSRF через `GET /auth/csrf`; до его успеха нельзя отправлять формы. HttpOnly-сессия остаётся в cookie, пользователь и токены не записываются в localStorage. Загрузка не показывает защищённый контент. Охранник повторно проверяет сессию после login/password и при возвращении в приложение. 401 от защищённой операции удаляет персональный query-cache; повтор мутаций автоматически запрещён.
2. **Маршруты.** `/login`, `/register` доступны гостю. Вошедший с обычным паролем попадает с них на `/`; `mustChangePassword` ведёт на `/password/change`. Любой защищённый URL для гостя ведёт на `/login`, для временного пароля — на `/password/change`. При таком флаге не рендерить навигацию других разделов. `/styleguide` остаётся публичной технической витриной. Смена пароля доступна и вошедшему без флага через меню пользователя. Внешние redirect URL не принимаются; после входа переход на `/`.
3. **Вход (R3).** Поля «Email», «Пароль», кнопка «Войти», ссылка на регистрацию. LoginRequest допускает старый пароль длиной 1–1024: правило нового пароля не применяется при входе. INVALID_CREDENTIALS показывает единое «Неверный email или пароль». EMAIL_NOT_VERIFIED просит подтвердить email, без неработающей ссылки на U15. Во время отправки повтор блокируется. После успеха получить свежий CSRF, актуализировать сессию; при неуспехе обновления CSRF объяснить ошибку и дать повторить только обновление, не повторяя успешный login.
4. **Регистрация (R1, R2).** `/register` переключает «Студент / Преподаватель». Общие поля — ФИО, Email, Пароль; студент выбирает факультет и затем группу. Преподаватель выбирает факультет как фильтр справочника и кафедру, в запрос уходит только departmentId. Пока факультет не выбран, зависимое поле отключено. Смена факультета/роли сбрасывает зависимый выбор; старый ответ не подставляет выбор другого факультета. Нет факультетов/групп/кафедр — объяснение пустого состояния, отправка невозможна; ошибка справочника — повтор. Выбор кафедры не объявляется допуском.
5. **Ограничения полей.** ФИО после trim непустое, максимум 200; email непустой корректный адрес, максимум 254. Новый пароль минимум 8 символов, максимум 72 UTF-8 байта; 36 букв «я» допустимы, 37 — нет. Пароли не trim и не логировать. Серверная VALIDATION_FAILED с корректными fieldErrors отображается у соответствующих полей с русским текстом. EMAIL_TAKEN — ошибка email; EMAIL_RESERVED_FOR_TEACHER — предложение выбрать роль преподавателя. Неизвестная/сетевая ошибка — понятное сообщение без сырого ответа. Смена поля убирает его устаревшую ошибку, остальные ошибки сохраняются.
6. **Итог регистрации (R1, R8).** 201 не создаёт сессию и не вызывает автоматический login. `nextStep: LOGIN` — текст «Регистрация завершена. Теперь можно войти» и ссылка на вход; `CONFIRM_EMAIL` — просьба открыть письмо, без выдуманного resend API. Пароль очищается после успеха. Не показывать фиктивный баланс: начальные 1000 АР начисляет backend, профиль — другой юнит.
7. **Настройки (R47, R48).** Из `GET /auth/config` показывать «Демо-стенд: данные могут быть сброшены» только при demo=true; «Подтверждение email на этом стенде выключено» только при OFF. При загрузке/ошибке конфигурации не подставлять OFF по умолчанию; регистрация недоступна до загрузки, есть повтор. Login не блокируется отказом необязательной конфигурации; сообщения режима не выдумываются.
8. **Смена пароля (R49, R50).** Поля «Текущий пароль», «Новый пароль», кнопка «Сменить пароль». Старый пароль 1–1024, новый по п. 5. PASSWORD_REUSED у нового поля; MISMATCH у currentPassword. POST `/auth/password` 204 → свежий CSRF и перечитать me; только серверный mustChangePassword=false открывает разделы. Текущая сессия сохраняется. При флаге видны объяснение и выход; ссылок на продуктовые разделы нет. Пароли очищаются после успеха.
9. **Выход и ограничения (R2, R3).** Меню пользователя содержит «Мой профиль», «Сменить пароль», «Выйти»; у администратора ссылка на свой `/users/:id` допустима по UX-карте. Успешный logout очищает весь персональный cache и ведёт на login, затем получает CSRF; отказ logout не выдаётся за успешный выход. Teacher с teacherApproved=false видит на главной «Заявка ждёт подтверждения администратора»; backend остаётся источником прав. STUDENT/PENDING видит пояснение о членстве, если такой ответ пришёл из будущего U15. Остальные разделы до своих юнитов сохраняют существующие заглушки.
10. **Внешние ответы.** Разбирать API-ответы на границе: объект CurrentUser с валидной ролью и обязательными полями, AuthConfig, RegistrationResult, списки справочников и fieldErrors. Не приводить произвольный JSON к типу через `as`. Не смешивать состояние гостя, загрузку, ошибку и вошедшего: discriminated union/query status. QueryClient один на приложение, тесты изолируют его; test helper повторяет production-провайдеры. Статический SessionProvider из скелета заменяется серверным источником, регрессии навигации проверяются с полными контрактными fixtures.
11. **Вид (R40, ADR009).** PageLayout/FormLayout и общая тема, спокойная полоса заголовка и компактная форма, без нового набора цветов. Переключатель трёх тем доступен до входа и после; выбор через существующий механизм. На 360/1280 нет горизонтальной прокрутки, поля имеют label/autocomplete (email/current-password/new-password/name), ошибки aria-describedby/alert, состояния загрузки role=status; основные действия и меню доступны клавиатурой. Цели ≥44 px, высокий контраст ≥52 px. Тестирование не объявляет весь U23 выполненным.

## Порядок и проверка

1. Tester пишет `frontend/src/features/auth/*.acceptance.test.tsx` и test-only fixtures/helper по матрице. RED запускается на скелете: неработающий login/register/password/session, а не синтаксическая ошибка; отчёт с кодом выхода и причиной. Тесты используют реальные routes, TanStack Query и MSW, не мокают сами auth hooks.
2. Исполнитель: границы данных и session-query → login/CSRF → регистрация/справочники → password/logout/guard → визуальная сверка. Самостоятельные unit-тесты разрешены, acceptance неизменны.
3. `npm --prefix frontend run check`, `npm --prefix frontend run build`; `node tools/check-agent-docs.mjs`; `node --test "tools/test/*.test.mjs"`. API не меняется, генерация не требуется; проверить отсутствие generated diff.
4. `docker compose up -d --build --wait` без удаления томов вручную: локальный demo-профиль сам пересоздаёт данные по R47. Браузер на `http://localhost:8080`: login демо-студента → reload → logout; регистрация уникального синтетического студента → вход; demo-администратор с временным паролем → принудительная смена → logout/login новым паролем; преподаватель без допуска. Только локальные синтетические данные.
5. На 360 и 1280 открыть login/register/password в трёх темах, сохранить скриншоты, измерить ширину и touch-target, проверить ошибки и клавиатуру. Записать фактический результат и ограничения в `docs/reviews/u5-auth/verification.md` и agent-log. Без независимого approve юнит не считается принятым и не сливается.
