# U9 frontend — активности, подтверждение и бюджет

## Goal Capsule

- **Цель.** Студент видит активности своей группы и управляет записью на общественные. Преподаватель создаёт активности, подтверждает участие по серверному предпросмотру, видит бюджет, историю и статистику начислений. Экраны работают в принятой теме от 360 px.
- **Источники.** Мастер-U9: R3, R17–R21, R41; AE8–AE10; KTD3, KTD5, KTD18, KTD23. `docs/spec/api/openapi.yaml`: activity-операции и `getMyAwardsSummary`, `listMyAwards`, `listAccessibleGroups`. UX: `screen-map.md`, каркасы С4/П2, ADR009, glossary, `frontend/AGENTS.md`.
- **Граница.** Только frontend. Backend, Liquibase, API-контракт и generated-файлы не меняются; все activity-операции пока planned. Для разработки — явный `VITE_API_MOCKS=true`; production UI всегда вызывает API, не переключается на моки по ошибке сервера.
- **База и публикация.** Ветка `u9-activities-frontend` от `ccdfd5d` (PR33). До принятия PR33 новый PR базируется на `u5-auth-frontend`, чтобы diff содержал только U9; после принятия родителя — база main и повтор проверки интеграции. Коммит/пуш/PR — после зелёных ворот по сохранённому поручению человека публиковать готовые юниты. Самоприёмка не заменяет независимое ревью.
- **Тесты.** Отдельная сессия tester пишет acceptance до production по корневому AGENTS.md. Человек 11 ноября разрешил запускать тестировщиков для дальнейших frontend-юнитов без дополнительных вопросов. Исполнитель её ожидания не меняет. Обычные дополнительные unit-тесты исполнителя допустимы.

## Наблюдаемое поведение и границы

1. **Маршруты и роли (R3).** `/activities` — STUDENT/TEACHER; `/activities/new`, `/activities/:id/confirm`, `/groups` — TEACHER. Гость и временный пароль проходят существующий auth-guard. Для другой роли — «Нет доступа», без вызова недоступного API. Некорректный id — «Активность не найдена», без запроса с NaN. Backend остаётся источником авторизации; API 403/404 отображаются понятным текстом, а не пустым списком.
2. **Список (R17/R18).** Заголовок «Активности», фильтр «Все / Учебные · БУА / Общественные · БОА». Сохранять серверную сортировку (будущие по возрастанию, прошедшие от недавних); не пересчитывать её по часам браузера. В строке/карточке — название, описание, тип/валюта, максимум, начало по Москве, автор со ссылкой на `/users/:id`, группы. Студент видит свою запись и уже начисленные сумму/уровень. Учебная активность объясняет отсутствие записи. Loading/empty/error с retry обязательны; пустой фильтр объясняет, каких активностей нет.
3. **Запись (R18).** Для SOCIAL и enrollmentOpen=true: enrolled=false — «Записаться», enrolled=true — «Отменить запись». При PENDING-членстве запись заблокирована и объяснена; отмена уже существующей записи разрешена независимо от членства, пока enrollmentOpen=true (контракт DELETE). При закрытой записи нет активной кнопки изменения; при enrolled=null не выдавать null за false. Время открытия берётся из API-флагов, не Date.now. PUT/DELETE без тела, с общим CSRF; во время запроса повтор блокируется. Успех инвалидирует list/get; 422 ENROLLMENT_CLOSED обновляет состояние и объясняет закрытие; MEMBERSHIP_NOT_ACTIVE/GROUP/FORBIDDEN — понятная причина, без ложного успеха. PENDING не скрывает сам список.
4. **Создание (R17/R41).** Преподавателю — ссылка «Создать активность». Форма: «Название» 1…200 после trim, «Описание» до 10000, «Тип активности» ACADEMIC/SOCIAL, «Группы» из accessible-groups (одна или несколько, уникальные id), «Дата и время начала (Москва)», «Максимум баллов» целое 2…10000. Начальные поля пустые, тип учебный. Ввод даты независимо от зоны браузера преобразуется из Europe/Moscow в UTC; проверяется корректность календаря и будущее относительно внедряемого Clock. Из внешнего UI-ввода значения проверяются один раз. Групп нет — объяснение допуска/доступа, submit недоступен; ошибка справочника — retry. API fieldErrors показываются у полей, старые ошибки снимаются при исправлении. POST 201 ведёт на список и инвалидирует его; никакого начисления при создании UI не делает.
5. **Подтверждение (R19).** Экран читает Activity и ParticipantList по id; author должен быть текущим TEACHER. До confirmationOpen=true — объяснение даты начала и нет отправки preview/confirm. SOCIAL получает участников только из серверного списка записавшихся; ACADEMIC — из списка активных студентов целевых групп, UI не строит их самостоятельно. Студент: ФИО/ссылка, группа, выбор checkbox, уровень 25/50/75/100 %. Изначально никто не выбран; выбранному по умолчанию 100 %. Радиогруппа доступна только выбранному и неподтверждённому. Подтверждённая строка — дата, уровень, сумма и только просмотр. Запрос содержит уникальные studentId, 1…500 элементов; при 500 новых выбор остальных блокируется с объяснением. Ошибочные/пустые ответы и повтор id не приводят к повторным строкам начисления.
6. **Предпросмотр (R19/R20, AE8/AE9).** Для непустого выбора вызывается POST participation/preview с тем же телом, что у confirm; CSRF обязателен. В UI показываются только суммы, total и бюджеты этого ответа, без собственной формулы начисления. Query key включает id и весь выбранный набор/уровни, запросы отменяются через AbortSignal; старый ответ после смены выбора не разрешает подтверждение. Пока preview грузится/ошибочен/обновляется, submit недоступен. Видны по каждой группе нужно/остаток/не хватает. withinBudget=false блокирует подтверждение целиком и объясняет изменение выбора. Пример: максимум 75, уровень 50, сумма из preview 38; при двух по 50 и остатке 50 — нужно 100/не хватает 50, confirm не отправляется.
7. **Итог и гонки (R19/R20, AE8/AE10).** Кнопка называет серверный итог «Начислить N БУА/БОА». Успешный ParticipationResult даёт «Начислено N …» без заливки; alreadyConfirmed объясняется отдельно, total=0 не выдаётся за новое начисление. После успеха сбросить только локальный выбор и инвалидировать participants/activity/list/budgets/history/summary; серверные строки не копируются в useState. Пока participants обновляются, повторный выбор из старых строк заблокирован. 422 BUDGET_EXCEEDED может прийти после положительного preview: показать группы с дефицитом, ни одного ложного успешного итога, обновить preview/бюджеты. NOT_ENROLLED/STUDENT_NOT_ELIGIBLE/ALREADY_CONFIRMED показывают имена студентов из проверяемого studentIds и обновляют участников. INVALID_STATE объясняет закрытое подтверждение. Автоповтора confirm нет; явный повтор безопасен по серверной идемпотентности, UI не начисляет ничего самостоятельно.
8. **Бюджет и история (R20/R21).** `/groups`: заголовок «Группы и бюджет», поле «Месяц бюджета» YYYY-MM. Первоначально месяц берётся из BudgetList (серверный текущий, по Москве), не из часов компьютера. Видны лимит/расход/остаток по группам и общая статистика месяца с разбивкой по валютам из summary. Удалённый доступ не скрывает группы своих прежних активностей/историю: UI использует возвращённые budgets/summary и не обрезает их accessible-groups. История из me/awards с фильтром группы/месяца, новые сверху; на строке студент/активность, группа, уровень, сумма/валюта, дата по Москве. Смена месяца сбрасывает группу, меняет query key и начинает курсор с первой страницы. IntersectionObserver подгружает nextCursor; «Показать ещё» остаётся клавиатурной альтернативой. Не суммировать только загруженную историю вместо server summary. Дубликаты id при склейке страниц не отображать.
9. **Ошибки, данные и вид.** API-ответы разбираются на входе: положительные безопасные числовые id, enums, целые суммы/уровни, ISO timestamps, обязательные поля/nullable-варианты и списки. Для activity-валюты допустимы только согласованные ACADEMIC/BUA или SOCIAL/BOA. Malformed-ответ — ошибка с retry, а не unsafe cast/фиктивные нули. Сетевые ошибки не превращаются в пустоту. Все server-state — TanStack Query, повтор mutation=false. PageLayout/FormLayout/TeacherTableLayout и токены ADR009; на мобильном таблица превращается в подписанные строки без горизонтального скролла. Управление с label/aria, видимый фокус, мягкие статусы и текстовые итоги; три темы, цели ≥44/52 px, контраст ≥4.5/7. Не объявлять полный U23 выполненным.
10. **Моки и проверка.** Factory handlers получают Clock и данные generated examples, не хранят второй auth-state. Симулируют список/создание/запись/предпросмотр/подтверждение/бюджеты/историю для студента и преподавателя, сохраняют изменения в памяти mock-API и корректно реагируют на месяц/группу/cursor. Расчёт в fake API служит только разработке интерфейса и не импортируется production-компонентами. Не править backend и не менять planned в контракте. Browser QA — web dev внутри локального compose с явно включённым MSW; проверка реальной интеграции activity-backend отложена до его реализации и отдельно отмечена.
