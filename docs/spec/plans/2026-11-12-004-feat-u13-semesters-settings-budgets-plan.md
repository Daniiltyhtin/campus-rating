# Дать администратору семестры, настройки и бюджеты - Plan

**Target repo:** campus-rating

## Goal Capsule

- **Objective:** администратор ведёт семестры (с «Начать сейчас»), меняет настройки штрафа, начисления семестра и лимита бюджета и видит бюджеты преподавателей — без SQL и переменных окружения.
- **Authority:** Requirements → Acceptance Examples → Key Decisions → исходное ТЗ хакатона (модуль 8) и мастер-план (R9, R20, R26) → Sources.
- **Open blockers:** нет. Правила, на которые ссылаются R (мастер-план, текущий код), читаются в репозитории `campus-rating`; здесь повторены только те, что меняются.

## Product Contract

### Summary

Три экрана администратора — «Семестры», «Настройки», «Бюджеты» — и обновлённое меню администратора. Семестры идут строго по порядку дат; N начисления фиксируется в семестре при его начале; снижение лимита ниже потраченного предупреждает до сохранения.

### How This Work Fits Together

- Остаток мастер-U13 разбит на четыре файла требований (2026-11-12): `2026-11-12-004-feat-u13-semesters-settings-budgets` (этот), `2026-11-12-005-feat-u13-import`, `2026-11-12-006-feat-u13-users-temporary-passwords`, `2026-11-12-007-feat-u13-admin-submission-view`.
- Экраны допуска преподавателей и выдач — готовый план `docs/spec/plans/2026-11-11-004-feat-u13-teachers-frontend-plan.md`, сюда не входят. Старосты (R27) отложены вместе с мастер-U15.
- Этот файл первым: он задаёт меню администратора, на пункты которого ссылаются остальные.

### Problem Frame

- **Кто:** администратор стенда.
- **Сейчас:** семестры «Осень 2026» и «Весна 2027» заданы миграцией; шаг (4 АР) и интервал (60 с) штрафа, N семестра (200 АР) и лимит бюджета (1000 в месяц) — переменные окружения, строка в таблице `settings` перекрывает их только через SQL. Бюджеты видит только сам преподаватель. В меню администратора есть пункт «Старосты» без экрана.
- **Зачем:** исходное ТЗ, модуль 8: «Управление семестрами и настройками: начисление АР в начале семестра, параметры списания, бюджеты преподавателей».
- **Риски данных:** каждое начало семестра пишет проводки `SEMESTER_ACCRUAL` всем студентам; проводки не отменяются. Ошибочное начало семестра не откатить.

**Термины.** *Сравнение строк* во всех файлах U13: пробелы по краям обрезаются; email сравнивается без учёта регистра (как уникальность `app_user`); названия — без учёта регистра; коды справочников — как сейчас в «Справочниках». Сортировка «по ФИО» — как в остальных списках приложения (порядок БД).

 *Семестр* — название и момент начала. *Начат* — момент начала наступил (по часам сервера). *Запланирован* — момент начала в будущем. *N семестра* — сколько АР начисляется каждому студенту при начале семестра со срезкой до 1000.

### Requirements

**Меню администратора**

- R1. Пункты меню администратора: «Справочники», «Пользователи», «Импорт», «Семестры», «Настройки», «Бюджеты». Пункт «Старосты» убран до мастер-U15 (источник: пользователь, интервью — старосты отложены).

**Семестры (`/admin/semesters`)**

- R2. Список: все семестры по возрастанию момента начала; колонки — название, начало (дата и время по Москве), состояние «Начат» или «Запланирован», N (для начатых — зафиксированное; для запланированных — «—») (источник: пользователь, интервью; мастер-R26).
- R3. Создание: название (1–100 символов после обрезки пробелов по краям, уникально без учёта регистра) и начало (дата и время по Москве, с точностью до минуты). Начало нового семестра строго позже текущего времени и строго позже начала всех существующих семестров (источник: пользователь, интервью; «позже текущего времени» — предложение: семестр с прошедшей датой начинается кнопкой R5).
- R4. Правка названия и начала и удаление — только у запланированного семестра. При правке редактируемый семестр в сравнении R3 не участвует, а новое начало — строго позже текущего времени и начала предыдущего семестра и строго раньше начала следующего (порядок семестров не меняется). У начатого кнопок правки и удаления нет; API отклоняет и правку, и удаление начатого: «Семестр уже начался — изменить нельзя» (источник: пользователь, интервью; правило соседей — предложение).
- R5. «Начать сейчас» — только у ближайшего запланированного семестра (самое раннее начало среди запланированных). Подтверждение: «Начать семестр «<название>» сейчас? Каждому студенту начислится до <N> АР. Отменить начисление будет нельзя.», если есть начатый семестр — дополнительной строкой «Предыдущий семестр «<название>» начат <дата и время по Москве>.», кнопки «Начать» и «Отмена». Запуск подряд нескольких семестров разрешён: каждый начисляет по R7 (ущерб ограничен срезкой до 1000) После подтверждения момент начала — текущее время сервера, семестр «Начат». N в тексте — текущая настройка на момент открытия диалога; начисляется N, действующее в момент нажатия «Начать» (R6). API отклоняет запуск не ближайшего семестра: «Начать сейчас можно только ближайший запланированный семестр» (источник: мастер-R26, пользователь, интервью; тексты — предложение).
- R6. N фиксируется в семестре из текущей настройки: при «Начать сейчас» — в момент нажатия «Начать»; при наступлении даты — когда задание начисления (раз в минуту) впервые видит семестр начатым. Дальнейшая смена настройки на начатый семестр не влияет (источник: пользователь, интервью).
- R7. Начисление начатого семестра — как сейчас, по мастер-R9: каждому студенту, зарегистрированному не позже момента начала, один раз начисляется `min(N, max(0, 1000 − АР))`; АР больше 1000 не уменьшаются; повторного начисления за тот же семестр нет, в том числе когда начисление дало 0 (источник: мастер-R9).
- R8. Нарушение R3 — под полем «Начало»: «Начало должно быть позже начала семестра «<название последнего>»»; повтор названия — под полем «Название»: «Семестр с таким названием уже есть» (источник: пользователь, интервью; тексты — предложение).

**Настройки (`/admin/settings`)**

- R9. Поля и границы (включительно): «Шаг штрафа, АР» — 1…1000; «Интервал штрафа, с» — от `ceil(2 × campus.penalty.poll-period)` секунд (по умолчанию `poll-period` = 1 с, минимум 2 с) до 86 400; «Начисление семестра, АР» — 0…1000; «Лимит бюджета в месяц» — 0…100 000. Только целые числа; дробное или пустое значение — как вне границ. Вне границ — под полем «Допустимо от <мин> до <макс>», API отклоняет `VALIDATION_FAILED` с ошибкой по полю (источник: пользователь, интервью; текст — предложение).
- R10. Сохранение одной кнопкой «Сохранить»; успех — «Настройки сохранены». Изменения действуют: шаг и интервал — для точек, созданных после сохранения (мастер-R7); N — для семестров, начатых после сохранения (R6); лимит — сразу для всех проверок бюджета (мастер-R20) (источник: мастер-R7, R20, R26; пользователь, интервью).
- R11. Если новый лимит меньше прежнего и в текущем месяце (по Москве) есть пары «преподаватель + группа» с расходом больше нового лимита, до сохранения — подтверждение: «Пар «преподаватель + группа», у которых расход в этом месяце уже больше нового лимита: <K>. Их остаток станет 0, новые начисления в эти группы до конца месяца будут отклоняться.», кнопки «Сохранить» и «Отмена». K считается при открытии диалога; «Сохранить» сохраняет все поля формы без повторной проверки; «Отмена» не сохраняет ничего, форма остаётся с введёнными значениями. Расход — как в «Потрачено» на экране «Группы и бюджет» (источник: Q1 плана U9–U11, мастер-U13; текст — из решения Q1, уточнён).

**Бюджеты (`/admin/budgets`)**

- R12. Таблица пар «преподаватель + группа», у которых за выбранный месяц расход больше 0 (расход считается так же, как «Потрачено» на экране «Группы и бюджет»): преподаватель (ФИО — ссылка на профиль `/users/:id`), группа, лимит, потрачено, остаток (`max(0, лимит − потрачено)`). Лимит — текущая настройка для любого месяца: история лимитов не хранится (предложение). Сортировка: ФИО преподавателя, затем название группы. Месяц по умолчанию — текущий по Москве, выбор месяца полем «Месяц». Только просмотр (источник: пользователь, интервью; исходное ТЗ, модуль 8; мастер-R20).
- R13. Нет начислений за месяц — «За <месяц год> начислений не было» (источник: предложение).

**Доступ**

- R14. Все экраны и операции этого файла — только администратору; остальным — «Нет доступа» на экране и `403` в API; до смены временного пароля — как сейчас (`PASSWORD_CHANGE_REQUIRED`) (источник: мастер-R3, R24; код, как сейчас).

### Key Decisions

- **Семестры строго по порядку** (session-settled: user-approved — chosen over «независимые семестры» и «“Начать сейчас” только когда все прочие начаты»: порядок начислений совпадает с порядком дат). Governs R3, R4, R5, R8.
- **Двойной старт разрешён с предупреждением** (session-settled: user-approved — chosen over «дата окончания семестра» и «запрет “Начать сейчас” раньше N дней после предыдущего»: кнопка нужна для демо, ущерб ограничен срезкой до 1000). Governs R5.
- **N фиксируется при начале семестра** (session-settled: user-approved — chosen over «N на момент обработки студента»: одинаковое начисление всем студентам семестра). Governs R2, R6, R10.
- **Бюджеты — только просмотр пар с расходом** (session-settled: user-approved — chosen over «только общий лимит» и «персональный лимит пары»: закрывает пункт ТЗ без смены правила R20). Governs R12, R13.

### Acceptance Examples

Время — Москва. Каждый AE начинается с чистого стенда demo (миграции + демо-история), текущее время сервера — 13.11.2026 12:00. «Осень 2026» начат 01.09.2026 00:00, «Весна 2027» запланирован на 09.02.2027 00:00; настройки: шаг 4 АР, интервал 60 с, N = 200, лимит 1000.

- AE1. **Covers R1.** Дано: вход администратором. Тогда: меню «Справочники, Пользователи, Импорт, Семестры, Настройки, Бюджеты»; «Старосты» нет.
- AE2. **Covers R2.** Тогда: строки «Осень 2026 · 01.09.2026 00:00 · Начат · 200» и «Весна 2027 · 09.02.2027 00:00 · Запланирован · —».
- AE3. **Covers R3, R8.** Когда: создать «Лето 2027» с началом 01.06.2027 00:00. Тогда: создан, «Запланирован». Когда: затем создать «Зима» с началом 01.01.2027 00:00. Тогда: под «Начало» — «Начало должно быть позже начала семестра «Лето 2027»». Когда: «весна 2027» с началом 01.09.2027 00:00. Тогда: «Семестр с таким названием уже есть».
- AE4. **Covers R4.** Тогда: у «Осень 2026» нет кнопок правки и удаления; запросы API на правку и на удаление — отказ «Семестр уже начался — изменить нельзя». Дано: создан «Лето 2027» с началом 01.06.2027 00:00. Тогда: правка его начала на 02.06.2027 00:00 проходит; правка начала «Весна 2027» на 05.06.2027 00:00 — отказ (позже следующего); удаление «Лето 2027» проходит.
- AE5. **Covers R5, R6, R7.** Дано: студент с АР 900, зарегистрирован до сегодняшнего дня; N = 200. Когда: «Начать сейчас» у «Весна 2027» и «Начать». Тогда: «Весна 2027» — «Начат», N 200, начало 13.11.2026 12:00; не позже чем через 2 минуты у студента АР 1000 (начислено 100); у студента с АР 1200 АР остаются 1200. Когда: «Отмена» в диалоге. Тогда: семестр «Запланирован», начислений нет.
- AE6. **Covers R5.** Дано: создан «Лето 2027» (01.06.2027 00:00). Тогда: «Начать сейчас» только у «Весна 2027», в подтверждении — «Предыдущий семестр «Осень 2026» начат 01.09.2026 00:00.»; после запуска «Весна 2027» «Начать сейчас» появляется у «Лето 2027». До этого запрос API на запуск «Лето 2027» — отказ «Начать сейчас можно только ближайший запланированный семестр».
- AE7. **Covers R6, R10.** Дано: «Весна 2027» начат с N 200. Когда: N меняют на 100. Тогда: у «Весна 2027» N 200; следующий начатый семестр получает 100.
- AE8. **Covers R9.** Когда: шаг 0, интервал 1 с, начисление 1001, лимит −5. Тогда: под каждым полем «Допустимо от … до …», ничего не сохранено.
- AE9. **Covers R10.** Когда: шаг 10, «Сохранить». Тогда: «Настройки сохранены»; у новой точки «Штраф: 10 АР каждые 60 с»; у точки, созданной до этого, — «Штраф: 4 АР каждые 60 с». Когда: интервал 120 с. Тогда: у новой точки «каждые 120 с», у старых — прежний. Когда: шаг 2,5. Тогда: «Допустимо от 1 до 1000».
- AE10. **Covers R11.** Дано: у Петрова в ИВТ-21 в текущем месяце потрачено 950, лимит 1000. Когда: лимит 500, «Сохранить». Тогда: подтверждение «Пар «преподаватель + группа», у которых расход в этом месяце уже больше нового лимита: 1. Их остаток станет 0, новые начисления в эти группы до конца месяца будут отклоняться.»; после «Сохранить» у Петрова на «Группы и бюджет» остаток ИВТ-21 — 0; подтверждение участия на 1 балл в ИВТ-21 — отказ «не хватает бюджета». При «Отмена» лимит 1000.
- AE11. **Covers R12, R13.** Дано: демо-история. Тогда: на «Бюджеты» за ноябрь 2026 строки «Петров П. П. · ИВТ-21 · 1000 · 950 · 50» и «Петров П. П. · ИВТ-22 · 1000 · 500 · 500». Когда: месяц — январь 2026. Тогда: «За январь 2026 начислений не было».
- AE12. **Covers R14.** Дано: вход преподавателем, затем студентом. Когда: открыть `/admin/semesters`, `/admin/settings`, `/admin/budgets` и вызвать их API. Тогда: «Нет доступа» на экранах, `403` в API.

### Success Criteria

- Демо-стенд обслуживается без SQL: начало семестра, смена настроек и просмотр бюджетов делаются с экранов.

### Scope Boundaries

Не входит:
- Персональный лимит бюджета для пары «преподаватель + группа».
- Старосты (R27) — вместе с мастер-U15.
- Изменение и удаление начатых семестров; откат начисления.

### Dependencies / Assumptions

- Демо-сид и миграция семестров не меняются; N у семестров, начатых до выкатки, фиксируется значением настройки в момент миграции (на стенде demo — 200). Некритично: начисление по ним уже прошло, N только показывается.
