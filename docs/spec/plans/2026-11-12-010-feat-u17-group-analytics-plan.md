## Product Contract

### Summary

Вкладка «Аналитика» рядом с текущим рейтингом группы. Общий выбор периода управляет графиком среднего АР и таблицей баллов за период; блок бюджета всегда показывает последние 6 месяцев. Преподаватель видит доступные группы и свой бюджет; администратор — любую группу и бюджет всех преподавателей группы.

### Problem Frame

- **Кто:** преподаватель с допуском (группы факультета кафедры и выдачи — мастер-KTD23); администратор.
- **Сейчас:** `/groups/:id` — рейтинг студентов по АР, БУА, БОА за всё время (мастер-U11, `frontend/src/features/feed/GroupRatings.tsx`), только преподавателю. Бюджет — экран «Группы и бюджет» за текущий месяц (`features/activities/BudgetPage.tsx`) и «Бюджеты» администратора (U13). Динамики нет.
- **Зачем:** исходное ТЗ, модуль 10: «Динамика академического рейтинга по группе, рейтинг студентов по БУА и БОА, статистика начислений и расхода бюджета по месяцам»; мастер-R36.
- **Риски данных:** нет. Аналитика только читает журнал проводок и членства; новых проводок, таблиц с данными и изменений журнала задача не создаёт.

**Термины.** *Сутки* — календарный день по Europe/Moscow. *Студент группы на момент T* — студент, чьё членство в группе `ACTIVE` и момент активации не позже T. Членство в системе не прекращается (выхода из группы нет), поэтому состав группы со временем только растёт. *АР студента на момент T* — сумма его проводок в АР с моментом не позже T. *Баллы за период* — сумма проводок `ACTIVITY_AWARD` в БУА или БОА с моментом внутри периода. *Начисление* — одна подтверждённая награда за участие (одна проводка `ACTIVITY_AWARD`). Проводки не отменяются и не корректируются. *ФИО по возрастанию* — порядок, как в остальных списках приложения (сортировка БД).

### Requirements

**Вкладки и доступ**

- R1. На `/groups/:id` две вкладки: «Рейтинг» (текущая таблица без изменений) и «Аналитика». По умолчанию открыта «Рейтинг»; выбранная вкладка — в адресе `?tab=analytics` (источник: карта экранов — «вкладка аналитики»; адрес вкладки — предложение).
- R2. Доступ: преподаватель — группы из доступных ему (как сейчас у рейтинга); администратор — любая группа, обе вкладки. Студенту и преподавателю без доступа к группе — «Нет доступа» на экране и `403` в API (источник: пользователь, интервью; мастер-R3, KTD23).
- R3. В «Справочниках» у каждой группы в строке — ссылка «Аналитика» на `/groups/<id>?tab=analytics` (источник: пользователь, интервью).

**Период**

- R4. Над вкладкой — выбор периода: «30 дней», «90 дней», «С начала семестра», «Свои даты». По умолчанию «30 дней». «30 дней» — сутки с (сегодня − 29) по сегодня включительно; «90 дней» — с (сегодня − 89) по сегодня. «С начала семестра» — с суток начала последнего начатого семестра по сегодня; если начатого семестра нет — пункт виден, но недоступен, с подсказкой «Семестр не начат». «Свои даты» — поля «С» и «По» (сутки, включительно), «По» не позже сегодня, «С» не позже «По», не больше 366 суток; иначе под полем «Допустимо не больше 366 дней, «С» не позже «По» и «По» не позже сегодня» (источник: пользователь, интервью; тексты и предел 366 — предложение).
- R5. Период действует на график R6 и таблицу R8; блок бюджета R10 от периода не зависит (источник: пользователь, интервью).

**Средний АР по дням**

- R6. График «Средний АР группы»: точка на каждые сутки периода — среднее АР студентов группы на конец суток (23:59:59,999 по Москве), округление до 0,1 по правилу «половина вверх» (1000,25 → 1000,3). Каждые сутки считаются заново по составу и балансам на их конец: проводки до начала периода учитываются, отдельного «переноса» значения нет. Сутки без студентов группы — без значения, линия прерывается (источник: мастер-U17, KTD3; правило округления — предложение).
- R7. Под графиком — таблица с теми же числами: «Дата», «Средний АР», «Студентов»; сутки без студентов — «—» в «Средний АР» и 0 в «Студентов». Порядок — по дате по возрастанию (источник: пользователь, интервью).

**Баллы за период**

- R8. Таблица «Баллы за период»: все студенты группы на конец периода; колонки — ФИО (ссылка на профиль `/users/:id`), «БУА за период», «БОА за период», «АР на конец периода». Студенты с нулём за период включаются (источник: пользователь, интервью).
- R9. Сортировка переключателем «БУА / БОА / АР», по убыванию; по умолчанию «БУА»; при равенстве — ФИО по возрастанию, затем id по возрастанию (источник: пользователь, интервью).

**Расход бюджета по месяцам**

- R10. Таблица «Расход бюджета по месяцам» за 6 календарных месяцев по Москве: текущий и 5 предыдущих, новые сверху. Преподавателю — его пара «преподаватель + группа»: «Месяц», «Лимит», «Потрачено», «Остаток», «Начислений», «БУА», «БОА». Администратору — строка на каждый месяц и каждого преподавателя с начислениями в группу за месяц, плюс колонка «Преподаватель»; внутри месяца — ФИО по возрастанию. Месяц без начислений — одна строка: «Преподаватель» — «—», «Лимит» — текущая настройка, «Потрачено» 0, «Остаток» — «—», «Начислений», «БУА», «БОА» — 0 (источник: пользователь, интервью; мастер-R20; строка пустого месяца и порядок — предложение).
- R11. «Потрачено» и «Остаток» считаются как на экране «Группы и бюджет»; «Лимит» — текущая настройка (история лимитов не хранится, как на «Бюджетах» U13) (источник: мастер-R20; план U13 004/R12).

**Пустые состояния**

- R12. В группе нет студентов на конец периода (членство не прекращается, значит, студентов нет и ни в одни сутки периода) — вместо графика, его таблицы и таблицы баллов один текст «В группе нет студентов с подтверждённым членством»; блок бюджета показывается (источник: предложение).

### Key Decisions

- **Общий выбор периода** (session-settled: user-approved — chosen over «свой период у каждого блока»: один фильтр проще проверить). Governs R4, R5, R6, R8.
- **Баллы за период вместо топ-5** (session-settled: user-directed — chosen over «считать закрытым существующей таблицей» и «топ-5»: фильтр по дате и сортировка по разным баллам). Governs R8, R9.
- **Администратор видит страницу группы** (session-settled: user-directed — chosen over «только преподаватель»; вход — `/groups/:id` и ссылка из «Справочников», user-approved). Governs R2, R3, R10.

### Acceptance Examples

Время — Москва, «сегодня» — 13.11.2026. Группа «Т-1» без других студентов, кроме названных.

Студенты: A — «Антонов Антон», B — «Борисов Борис», E — «Егоров Егор», все с членством `ACTIVE`. Начальные 1000 АР — проводка регистрации в момент активации.

- AE1. **Covers R6, R7.** Дано: A активирован 01.11 00:00 (1000 АР); 02.11 12:00 штраф A −20 АР; B активирован 03.11 10:00 (1000 АР). Период «Свои даты» 01.11–04.11. Тогда: 01.11 — 1000,0 (1 студент), 02.11 — 980,0 (1), 03.11 — 990,0 (2), 04.11 — 990,0 (2).
- AE2. **Covers R6, R12.** Дано: первый студент активирован 05.11. Период 01.11–06.11. Тогда: 01–04.11 — «—», линия начинается с 05.11. Дано: в группе нет студентов. Тогда: «В группе нет студентов с подтверждённым членством».
- AE3. **Covers R6.** Дано: студент C активирован 03.11 23:59:59 — входит в среднее 03.11; штраф C −5 АР в 04.11 00:00:00 — входит в 04.11, не в 03.11. Студент D с членством `PENDING` не входит ни в одни сутки. Дано: в сутки четыре студента с АР 1000, 1000, 1001 и 1000. Тогда: среднее 1000,25 показывается как 1000,3.
- AE4. **Covers R8, R9.** Дано: за 01–13.11 A получил 30 БУА и 0 БОА, B — 10 БУА и 50 БОА, E — ничего; 31.10 A получил 100 БУА; на конец 13.11 АР: A 980, B 1000, E 990. Период «Свои даты» 01.11–13.11. Тогда: «БУА» — Антонов (30), Борисов (10), Егоров (0); «БОА» — Борисов (50), Антонов (0), Егоров (0); «АР» — Борисов (1000), Егоров (990), Антонов (980). Награда 31.10 не учтена. ФИО — ссылки на `/users/<id>`. Дано: F «Фёдоров Фёдор» активирован 14.11. Тогда: в периоде 01.11–13.11 его строки нет.
- AE5. **Covers R4.** Когда: вкладка открыта впервые. Тогда: выбран «30 дней» — 15.10–13.11; «90 дней» — 16.08–13.11. Дано: «Весна 2026» начат 09.02.2026, «Осень 2026» — 01.09.2026 00:00. Тогда: «С начала семестра» — 01.09–13.11. Дано: начатых семестров нет. Тогда: пункт недоступен, подсказка «Семестр не начат». Когда: «Свои даты» 13.11.2025–13.11.2026 (366 суток). Тогда: принято. Когда: 12.11.2025–13.11.2026 (367 суток); 10.11–14.11.2026 («По» в будущем); 13.11–01.11.2026 («С» позже «По»). Тогда: в каждом случае ошибка из R4, данные не меняются.
- AE6. **Covers R10, R11.** Дано: Петров в ноябре начислил в ИВТ-21 950 баллов тремя начислениями (800 БУА, 150 БОА), в октябре — ничего; лимит 1000. Тогда у Петрова: «ноябрь 2026 · 1000 · 950 · 50 · 3 · 800 · 150», «октябрь 2026 · 1000 · 0 · 1000 · 0 · 0 · 0», в июне–сентябре начислений нет — 4 строки с нулями; майская строка не показывается. Дано: лимит изменён на 800. Тогда: во всех 6 строках «Лимит» 800, в ноябре «Остаток» 0. Дано: Волков в ноябре начислил 100 в ИВТ-21. Тогда у администратора за ноябрь две строки — Волков, затем Петров; у Петрова строки Волкова нет; у администратора за октябрь — строка «— · 1000 · 0 · — · 0 · 0 · 0».
- AE7. **Covers R2, R3.** Дано: Петрову доступна ИВТ-21; группа ЭК-11 другого факультета без выдачи. Тогда: Петров видит аналитику ИВТ-21; на ЭК-11 — «Нет доступа», API — `403`. Администратор: у каждой группы в «Справочниках» есть «Аналитика»; переход у ЭК-11 открывает обе вкладки. Студент на `/groups/<id ИВТ-21>` — «Нет доступа», API — `403`.
- AE9. **Covers R5.** Когда: период меняют с «30 дней» на «Свои даты» 01.11–04.11. Тогда: график и таблица под ним — 4 строки (01–04.11), таблица баллов — суммы за 01–04.11; таблица бюджета не меняется (те же 6 месяцев и значения).
- AE8. **Covers R1.** Тогда: `/groups/<id>` открывает «Рейтинг», таблица как раньше; `?tab=analytics` открывает «Аналитику»; переключение вкладок меняет адрес.

### Key Technical Decisions

- KTD1. **Код — в модуле `analytics`, чужие данные — только через публичные API.** Модуль уже объявлен (`backend/src/main/java/ru/campusrating/analytics/package-info.java`). Новые методы: `LedgerApi` — баланс АР студентов на момент и суммы проводок АР по суткам Москвы в интервале; суммы `ACTIVITY_AWARD` по студентам и валютам в интервале; начало последнего начатого семестра. `activity` — новый публичный интерфейс статистики бюджета пары/группы по месяцам. `analytics` не читает таблицы `ledger_entry`, `activity_*`, `group_membership` напрямую; `ModularityTest` это проверяет.
- KTD2. **Средний АР — в Java по ответу двух запросов.** Ledger отдаёт: баланс АР каждого студента на начало первых суток периода и изменения АР по суткам периода (группировка по суткам Europe/Moscow в SQL). Analytics накапливает баланс по суткам и делит на число студентов с `activatedAt` ≤ конца суток. Объём: ≤ 366 суток × студенты группы — без кэша и снимков (мастер-KTD3).
- KTD3. **Две операции API.** `GET /api/v1/groups/{groupId}/analytics?from=YYYY-MM-DD&to=YYYY-MM-DD` — период (сутки по Москве), ответ: группа, `semesterStart` (дата или `null`), сутки `{date, averageAr|null, students}`, строки баллов `{student, bua, boa, ar}`. `GET /api/v1/groups/{groupId}/analytics/budget` — 6 месяцев, строки `{month, teacher|null, limit, spent, remaining|null, awards, bua, boa}`. Сортировка таблицы баллов — на клиенте (R9: смена сортировки без запроса). Без `from`/`to` — последние 30 суток. Нарушение R4 — `VALIDATION_FAILED` с полем `from` или `to`.
- KTD4. **Доступ одним правилом.** Новый общий шаг: `ADMIN` — любая существующая группа; `TEACHER` — `TeacherScope.requireAccessible`; иначе `403`. Применяется в аналитике и в существующем `GroupRatingService` (R2: администратор видит обе вкладки). Несуществующая группа — `404` до проверки доступа, как сейчас у рейтинга.
- KTD5. **Графики — `@mantine/charts` (Recharts), версия в паре с `@mantine/core` 9.7.5.** Допущено мастер-планом для U17; свой SVG дороже. Табличная альтернатива под графиком — по R7.
- KTD6. **Округление и состояние вкладки.** Среднее округляется на сервере (`BigDecimal`, `HALF_UP`, 1 знак) — одно число для графика и таблицы. Вкладка и период — в адресе (`?tab=analytics&period=30|90|semester|custom&from&to`), обновление страницы сохраняет вид.

## Implementation Units

### U1. Контракт API

- **Goal:** две операции аналитики в контракте; рейтинг группы помечен доступным администратору.
- **Requirements:** R2, R4, R6–R11; KTD3, KTD4.
- **Dependencies:** нет.
- **Files:** `docs/spec/api/openapi.yaml`, `frontend/src/api/schema.d.ts`, `frontend/src/mocks/examples.generated.ts`.
- **Approach:** операции `getGroupAnalytics`, `getGroupAnalyticsBudget` с `x-roles: [TEACHER, ADMIN]`, явным `security` (сессия), ответами 400/401/403/404 и примерами; у `getGroupRating` добавить `ADMIN` в `x-roles`. Генерация — `npm run api:gen`.
- **Test expectation:** `redocly lint` контракта и `ContractCompatibilityIT` зелёные после U2–U4.
- **Verification:** `npx --no-install --prefix frontend redocly lint --config docs/spec/api/redocly.yaml docs/spec/api/openapi.yaml` без ошибок; сгенерированные файлы совпадают с контрактом.

### U2. Данные журнала и семестра

- **Goal:** методы `LedgerApi` для аналитики.
- **Requirements:** R4, R6, R8; KTD1, KTD2.
- **Dependencies:** нет.
- **Files:** `backend/src/main/java/ru/campusrating/ledger/LedgerApi.java`, `ledger/internal/LedgerService.java`, `ledger/internal/LedgerRepository.java`, `ledger/internal/SemesterRepository.java`, новые записи-результаты в пакете `ledger`, `backend/src/test/java/ru/campusrating/ledger/LedgerAnalyticsIT.java`.
- **Approach:**
  1. Баланс АР студентов на момент (сумма проводок `AR` с `created_at` ≤ момента).
  2. Изменения АР по суткам Москвы в интервале: группировка `created_at` в зоне Europe/Moscow.
