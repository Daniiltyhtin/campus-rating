# Тест-план Campus Rating

Юнит U12 мастер-плана ([план](plans/2026-10-31-001-feat-campus-rating-mvp-plan.md#u12-тест-план-и-e2e-базы)). Требования R и примеры AE — оттуда же, термины — [глоссарий](glossary.md).

Документ отвечает на три вопроса: что и чем проверяем, какое требование каким тестом закрыто и что получилось на последнем прогоне. e2e-тесты (`e2e/tests/base/`) пишутся по сценариям отсюда и ссылаются на их ID.

## 1. Уровни тестов

| Уровень | Инструмент | Что проверяет | Где лежит | Кто пишет | Где запускается |
|---|---|---|---|---|---|
| Доменные модульные | JUnit 6, PIT | Чистые функции: штраф по слотам, срезки, бюджет, округление уровня, статусы назначения | `backend/src/test/**/domain/` | агент скиллом `write-tests` до реализации | `mvnw verify`, CI |
| Интеграционные | Spring Boot Test, Testcontainers PostgreSQL 18 | SQL, транзакции, блокировки, идемпотентность проводок, события модулей | `backend/src/test/**/*IT.java` | агент, ревью человеком | `mvnw verify`, CI |
| Архитектура и контракт | Spring Modulith, oasdiff | Границы модулей; совместимость OpenAPI с реализацией | `ModularityTest`, `ContractCompatibilityIT` | агент | CI |
| Frontend | Vitest, Testing Library, MSW | Экраны против моков из примеров контракта, состояния загрузки/ошибки, тема | `frontend/src/**/*.test.ts(x)` | агент | `npm run check`, CI |
| e2e | Playwright, Chromium 360×800 и 1280×800 | Основные сценарии через UI на полном стеке с ускоренным штрафом | `e2e/tests/` | QA с агентом-тестировщиком | CI (`docker-compose.e2e.yml`) |
| Ручные и исследовательские | браузер, Android-эмулятор, API-скрипты | Сценарии защиты, граничные AE на реальных интервалах, мобильные проверки, права | раздел 6 и 8 этого документа | QA | локальный стенд `docker compose up` |

Пороги качества — в `backend/AGENTS.md` (JaCoCo ≥ 80 % и CRAP ≤ 10 в `*.domain`, PIT ≥ 70 % в `ledger`, `checkpoint`, `activity`).

## 3. Сценарии

Формат: ID, источник, предусловия, шаги, ожидание, негативные ветки, автотест. Все сценарии используют демо-аккаунты или регистрируют своих пользователей и не зависят от данных других сценариев.

### Регистрация и вход (R1–R3, R8)

**REG-01. Регистрация студента.** Источник: R1, R8.
- Предусловия: стенд demo, подтверждение email `off`.
- Шаги: `/register` → роль «Студент» → ФИО, email, пароль ≥ 8 → факультет → группа этого факультета → «Зарегистрироваться» → вход.
- Ожидание: аккаунт создан, вход проходит, в профиле 1000 АР, 0 БУА, 0 БОА.
- Негативные: пустые поля, пароль < 8, занятый email, группа другого факультета, некорректный email — ошибка под полем на русском, аккаунт не создан.
- Автотест: `e2e/tests/base/registration.spec.ts`.

**REG-02. Регистрация преподавателя и допуск.** Источник: R2, R3.
- Шаги: `/register` → «Преподаватель» → кафедра → вход.
- Ожидание: вход работает, на «Главной» плашка «Заявка ждёт подтверждения администратора», доступных групп нет; после допуска администратором группы факультета кафедры появляются.
- Негативные: email из списка преподавателей не регистрируется студентом.
- Автотест: `registration.spec.ts` (до допуска); допуск — после U13.

**AUTH-01. Вход, выход, сессия.** Источник: R3.
- Ожидание: неверный пароль и неизвестный email дают одинаковую ошибку; без входа любая страница ведёт на `/login`, API — 401; после выхода сессии нет; изменяющий запрос без CSRF-токена — 403.

### Контрольные точки и штраф (R7, R10–R16; AE1–AE4, AE6, AE7, AE11)

**CP-01. Создание точки.** Источник: R7.
- Шаги: преподаватель → «Новая точка» → название, описание, группы из доступных, дедлайн (МСК), стоимость → «Создать точку».
- Ожидание: точка в списке «Мои точки»; назначения у всех студентов выбранных групп с активным членством, статус «В процессе»; шаг и интервал зафиксированы из настроек.
- Негативные: стоимость 0 и > 1000, без групп, дедлайн в прошлом — 400; недоступная группа — 403; студент создать не может.

**CP-02. Сдача до дедлайна.** Источник: R10, R15.
- Шаги: студент → задача → ссылка или файл (pdf, docx, zip, png, jpg) → «Сдать работу».
- Ожидание: «Сдано на проверку», штрафа нет; новая сдача — новая версия, прежние видны в «Истории сдач».
- Негативные: пусто или ссылка и файл вместе — 400; недопустимый тип файла — ошибка; сдать чужое назначение — 403.

**PEN-01. Просрочка и потолок.** Источник: R11, R12, AE1.
- Предусловия: точка стоимостью 60, работа не сдана.
- Ожидание: в момент дедлайна штрафа нет; далее −20 за слоты 0, 1, 2; затем списаний нет; АР 940; статус «Просрочено», на странице задачи «Списано N из 60 АР».
- Автотест: `e2e/tests/base/checkpoint-penalty.spec.ts`.

**PEN-02. Сдача останавливает штраф.** Источник: R10, AE2.
- Ожидание: сдача после двух слотов — списано 40, дальше списаний нет.

**PEN-03. Возврат возобновляет штраф.** Источник: R12, R14, AE3.
- Шаги: после сдачи с опозданием преподаватель «Вернуть…» с комментарием.
- Ожидание: студент видит комментарий; штраф продолжается со следующего слота до общего потолка стоимости; уже списанное не обнуляется.
- Негативные: возврат без комментария — 400.

**PEN-04. Пол рейтинга.** Источник: R11, AE4.
- Ожидание: при АР 10 и стоимости 100 в слоте 0 списывается 10, при АР 0 проводки нет; после начисления семестра штраф продолжается, всего по точке не больше стоимости.

**PEN-05. Простой сервера.** Источник: R13, AE7.
- Шаги: после слота 0 остановить backend на несколько интервалов, поднять.
- Ожидание: пропущенные слоты не списаны; после подъёма списан текущий слот, дальше по расписанию.

**PEN-06. Параллельный проход планировщика.** Источник: AE6. Только интеграционный тест: за слот ровно одна проводка (ключ идемпотентности).

**CP-03. Приём работ.** Источник: R14.
- Шаги: страница точки → отметить одну или несколько работ → «Принять».
- Ожидание: принятые — «Принято», у студента в «Завершённых»; несданные в выборке пропускаются с `INVALID_STATE`.

**CP-04. Новичок в группе.** Источник: R16, AE11. Только интеграционный тест до появления подтверждения членства (U15).

### Семестр (R9; AE5)

**SEM-01. Начисление семестра.** Источник: R9, AE5.
- Ожидание: каждому студенту `min(N, 1000 − АР)`; при 1000 проводки нет; повторный проход того же семестра ничего не меняет; факт обработки сохраняется и при 0.

### Активности и бюджет (R17–R22; AE8–AE10)

**ACT-01. Создание активности.** Источник: R17.
- Ожидание: активность видна студентам целевых групп с типом и максимумом баллов.
- Негативные: максимум < 2 — 400; недоступная группа — 403; студент создать не может.

**ACT-02. Запись на общественную активность.** Источник: R18, AE10.
- Ожидание: запись и отмена до начала; на учебную записи нет (409); после начала запись закрыта.

**ACT-03. Подтверждение участия.** Источник: R19, AE9, AE10.
- Шаги: после начала → «Подтвердить участие» → студенты и уровень 25/50/75/100 % → предпросмотр → подтвердить.
- Ожидание: начислено `round_half_up(max × уровень / 100)` (50 % от 75 = 38) в валюте типа (`ACADEMIC` → БУА, `SOCIAL` → БОА); в истории студента: дата, `+38 БОА`, название, ФИО преподавателя.
- Негативные: подтверждение до начала — 409; незаписанный на `SOCIAL` — `NOT_ENROLLED`, проводок нет; уровень вне списка — 400; повторное подтверждение с другим уровнем — 409, второго начисления нет.
- Автотест: `e2e/tests/base/activity-budget.spec.ts`.

**BUD-01. Бюджет группы.** Источник: R20, R21, AE8.
- Ожидание: остаток уменьшается на сумму начислений; подтверждение сверх остатка отклоняется целиком (`BUDGET_EXCEEDED`) с остатком в ответе, проводок нет; в следующем месяце остаток снова равен лимиту.

**RAT-01. Рейтинг группы.** Источник: R22. Преподаватель видит студентов доступной группы с сортировкой по АР, БУА, БОА; студенту недоступно.

### Профиль и лента (R5, R6, R23)

**PRF-01. Профиль студента.** Источник: R5, R6.
- Ожидание: ФИО, факультет, группа, АР, БУА, БОА, история проводок в формате R6, активные и завершённые задачи; чужой профиль — без перехода к сдаче.
- Автотест: `e2e/tests/base/feed.spec.ts`.

**FEED-01. Лента наград.** Источник: R23.
- Ожидание: каждое начисление активности появляется в ленте у всех вошедших: студент, сумма с валютой, активность, преподаватель, дата; новые сверху.

### Нефункциональные (R39–R41, R47)

**NF-01. Запуск одной командой.** Источник: R39. `docker compose up` из чистого клона без `.env` — сервисы healthy, вход демо-аккаунтами работает.

**NF-02. Мобильная версия.** Источник: R40. Раздел 7.

**NF-03. Время.** Источник: R41. Дедлайны и время активностей показываются по МСК, ввод в форме — по МСК, в API — UTC.

## 6. Сценарий для защиты (ручной)

Порядок показа жюри; занимает около 7 минут. Стенд перезапустить перед показом, чтобы вернуть чистый сид.

1. `docker compose up` — стек поднимается одной командой (R39).
2. Регистрация нового студента ИВТ-21 на телефоне (360 px) → 1000 АР.
3. Петров (`petrov@campus.test`) создаёт точку «Курсовая, 1 этап» для ИВТ-21: стоимость 60, дедлайн через 1 минуту.
4. Студент видит задачу «В процессе»; ждём дедлайн — «Просрочено», «Списано 20 из 60 АР».
5. Студент сдаёт ссылку — штраф остановлен; Петров возвращает с комментарием — штраф идёт дальше; студент пересдаёт, Петров принимает.
6. Петров создаёт общественную активность (75 баллов), студент записывается, после начала Петров подтверждает 50 % → студенту 38 БОА, бюджет группы уменьшился.
7. Профиль студента: история проводок; лента наград — запись о начислении.

## 7. Мобильные проверки (R40)

На 360×800 (touch) и в Chrome на Android-эмуляторе для каждого экрана:

- нет горизонтальной прокрутки и элементов за краем экрана;
- нижняя навигация не перекрывает последний элемент страницы;
- нативные поля: выбор даты и времени дедлайна, выбор файла при сдаче, цифровая клавиатура для чисел;
- экранная клавиатура не закрывает кнопку отправки формы;
- тап-цели не меньше 24 px, основные кнопки — 40 px;
- тёмная тема и высокий контраст читаемы, выбор темы сохраняется после перезагрузки.
